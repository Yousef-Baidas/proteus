# Flow, step by step

The detail behind `SKILL.md`'s flow outline. Read a step's section when you reach it. `<hooks>` per `harnesses.md`.

## Session start

What `proteus-state` reports present is not redone or re-asked: `/setup-matt-pocock-skills`, `CONTEXT.md`, the conventions interview, `AGENTS.md ## Learned`, the roster and scout (`skills-unscouted=none`), skill linking (`skills-unlinked=none`), gates install, tracker labels (recorded in `## Learned`), `graphify` orientation, `stack.md`.

- **Pending review**: `gh issue list --label proteus-review --label needs-human --state open --json number,title -q …` (a question issue parks only its own tickets). Any open and the run attended → wait at step 7½, dispatching only speculative tickets (`review.md`).
- **Resume position**, from the tracker, first match wins: open PR into `proteus/<run>` with no verdict → step 6; with `MERGE` → step 7; open `proteus` issue with a `RED`/`NEEDS` comment → step 5; open `proteus` issue, no PR → step 4; the milestone's issues all closed, no review issue → step 7 QA then 7½; every milestone closed → step 8. Read the run-log tail the autostart printed before deciding. Resume an open run rather than start a second beside it.
- **Baseline on `main`**: `gh run list --branch main --limit 1 --json conclusion -q '.[0].conclusion'`; no CI → the gate command from `## Learned` with `>/dev/null 2>&1; echo $?`. Red → the stabilise ticket first (`bootstrap.md`), no feature dispatch. A gate run through the baseline ratchet counts as green while it reports no new findings (`enforcement.md` §12).
- **State notes**: `doc-bloat` not `none` → a docs-diet ticket joins the next wave (`docs-diet.md`); it does not block. `proteus-update` present → tell the human once. `scratch=` present → `node <hooks>/proteus-scratch.js --sweep --all-done`. `context-mode=missing` → tell the human once that it is optional and `install.js --doctor --fix` installs it. `skills-unlinked` not `none` → run that command (or ask the human to) before spawning an agent of a listed team, which would otherwise run without its skills. `sandbox=` not `on` while the session runs `bypassPermissions` → the guard refuses worker and verifier spawns; tell the human once to relaunch with the sandbox profile (`install.js --sandbox`). Any `NO` → step 0 for the missing pieces only.
- **No `models=` line** (no hooks yet): `judge` is your rung (the one under it on a once-per-project model like fable), `build` and `helper` one rung down, on haiku < sonnet < opus < fable; never under sonnet.

## Asking the human

- **Picker** (the run cannot move without the answer: grilling, roster approval, the information gate): `AskUserQuestion`, one to four questions per call, concrete options, your recommendation first and marked; it stays pinned until answered. Codex has no picker: plain numbered questions (`harnesses.md`).
- **Question issue** (everything else: a parked `NEEDS`, a dependency request with its OSV result, a `CONTRACT-UNCLEAR` you cannot settle, a missing `ROUTING.md` row, a proposed roster change): the `question` row of `tracker.md`. Park only the tickets that depend on it and keep dispatching the rest. `PushNotification` once. The human answers in `/proteus-review`, on GitHub, or by typing `questions` here. One issue per decision, not one per worker message.
- An answer that states a standing rule ("always", "never") also becomes a line in `CONVENTIONS.md` (the human's approval) or a lesson, so it is not asked twice.

## Tiers

`proteus-tier.js` reads the `tiers` block in `teams/ROUTING.md`; no block → Standard. The human's `full:` prefix raises a work order to Full; `quick:` lowers a Standard one to Quick, but not a Full one. Paths decide, not extensions: a skill repo's markdown is its product. Session start and the information gate apply to every tier.

- **Direct** (docs and typos within the block's limits): no ticket, contract, verifier, milestone or guide. A batch branch `proteus-work/direct/<batch>` from `origin/main`, its worktree prepared with `proteus-worktree.js <wt> --tier direct <paths>` (the next change in the batch re-runs it with every path so far). One `helper` with the Direct prompt (`roles.md`) makes the change and opens or extends one PR into `main`, its body the digest. CI's `direct` job runs the mechanical gates only. The human merges; that is the review. Add to a batch only while its PR is open.
- **Quick** (small, one team): one ticket without a milestone, one worker on `proteus-work/quick/<n>` from `origin/main`, its worktree prepared with `--tier quick` (`--human` after `quick:`). No contracts, debt issue, QA or guide; a verifier on `build` only when CI's gates cannot show the outcome. The PR goes into `main` with `Owned:` and `Tier: quick` (`quick (human)`) lines; the human merges.
- **Standard**: steps 0–8, `Tier: standard` on each PR; milestones that finish in the same wave share one QA pass and one review issue.
- **Full**: steps 0–8 as written, `Tier: full` on each PR.

An open Direct or Quick PR into `main` waits on the human and is not a run to resume. The ceiling check is `enforcement.md` §2.

## 0. Bootstrap

Read `bootstrap.md`, `tracker.md`, `domains.md`, `teams.md`; detect blank / mid-project / ready and take that path to its `Ready` line, with the roster approved and the domain's mechanical gates (`enforcement.md` on code, `domains.md` otherwise) installed. Lead docs go on local `main` (never pushed) until `proteus/<run>` exists, then by PR into it (`bootstrap.md`). `guest=<dir>` in the state line → guest mode (`bootstrap.md`): those docs and `teams/` live in that dir, and the repo gets no CI, lefthook or root doc. A `this repo is public` note → tell the human in your first reply that everything posted to the tracker and evidence branches is public.

## 1. Orient and the information gate

Read `AGENTS.md`, `CONTEXT.md`, relevant ADRs, and the taste docs `CONVENTIONS.md` names; their defaults go into every brief and spec now, not discovered in a review round. Unfamiliar repo → `graphify` once; the summary stays with you, since workers get no repo tour (`stack.md`).

Grill with `/grill-with-docs` when `CONTEXT.md` exists, `/grilling` on a blank repo, one question at a time until every gate item is filled. Work bigger than one milestone or one session → `/wayfinder` first, then the gate per destination. Unattended and a blank remains → park the work order, take the next. Already grilled (the run log says so) → skip.

Gate item (g), the threat model: the assets at stake, the trust boundaries the work crosses, and two to five abuse cases, each an observable outcome ("a user without the project role gets 403 on `PATCH /projects/:id`"). It applies when `proteus-tier.js <planned paths>` ends with a `threat model` line (a path matches the `security` block of `teams/ROUTING.md`, or the tier is Full); go by that line, not by globs read by eye. Each abuse case becomes a numbered check in its milestone's `ACCEPTANCE` (`review.md`), and every ticket that touches one gets a failing check for it in its contract (step 3).

### Refactor checkpoint

Standard and Full only; Direct and Quick skip it. The cheapest moment to clean an area up is before anything is built on it.

- A `helper` runs the scan phase of mattpocock `improve-codebase-architecture` (the skill `enforcement.md` §10 runs at close, read from its `SKILL.md`) over the modules the work order touches, and reports at most three refactor candidates, each with its cost to the planned work.
- No candidates → no question; log `refactor-checkpoint: none`.
- Candidates → one picker question with three options: **refactor first** (the candidates become a prep milestone ahead of the work), **defer to debt** (filed on the first milestone's debt issue, the way §10 files its scan), **ignore**.
- Log the answer on the run log as `refactor-checkpoint: <first|defer|ignore|none>`.

## 2. Tickets

Read `teams.md` again. `/to-spec`, then `/to-tickets`; every ticket becomes a tracker issue, every milestone a tracker milestone. Route each ticket by `teams/ROUTING.md` (no row → ask the human, then add the row via a ticket); owned paths inside that team's `Owns`; one owner per file among the tickets in flight; hotspot files (routes, registries, config, shared scene or project files) in a ticket that runs first; tags `difficulty:standard|hard` and `profile:<team>`. Two teams in one ticket → two tickets with a contract between them. A ticket whose outcome rests on facts outside the repo gets `needs-research` (its worker runs `/research` first). Milestones per `review.md`, one user-visible result each, acceptance checks frozen from gate item (b).

Script first (`roles.md`): the trigger is a procedure's second occurrence in the run, by you or a worker. Open the program ticket then, route it like any other, and log it on the run log as `script-ticket: <procedure> #<n>`, the ticket's number; later briefs call the program.

## 3. Contracts

Per ticket, write into the issue body the interface (code: exported signatures in a code block, `/codebase-design` vocabulary; otherwise the deliverable's shape per `domains.md`) and the check in one sentence: name, input, expected result. Can't write them → `/grilling` until you can. Create `proteus/<run>` once, its first commit recording every ticket's owned paths, the check's files among them, as `.proteus/owned/<id>`, and push it; a ticket added later is recorded through a lead-docs PR merged before its worktree is cut (`stack.md`). CI checks each worker's PR against that record on the run branch, which the worker cannot change. Then one worktree per ready ticket with the same paths and `--tier <tier>`. Under `install.js --sandbox`, every worktree is prepared in two steps, in this order: `proteus-worktree.js <wt> --tier <tier> <paths>` as usual, which prepares the whole worktree inside the sandbox, then the copy it names, `node ~/.claude/proteus-sandbox/bin/<hash>/proteus-worktree.js <wt>`, which runs outside it, writes nothing under the repo, and adds a new submodule's deny rules to the profile. `--allow` goes to the in-repo script. Then one contracts worker per team with ready tickets (`roles.md`; `judge`), all teams in parallel; it commits each ticket's stubs and check first on its branch and shows the check red twice, on the missing work and on a broken input. You do not open the files.

## 4. Dispatch

`node <hooks>/proteus-ready.js <run>` lists the ready tickets and why the rest wait; after each merge batch, run steps 3 and 4 for the new ones at once. Protect `proteus/<run>` (`enforcement.md` §1) so nothing merges without green CI. One PR per ticket into `proteus/<run>`, from the worktree made at step 3. Spawn `proteus-<team>-worker` if the repo defines one, else `proteus-worker` with the team named, the spawn's `model` set to `build` (prompt text does not change it). Before each spawn, the pre-dispatch check in `roles.md`. Start the stall watchdog now (`operations.md`). The scaffold and stabilise tickets follow `enforcement.md`.

With `isolation=container` in `proteus-state`, no Agent spawn for the worker: prepare the worktree as before, write the Worker brief (`roles.md`) to `<git-common-dir>/proteus/scratch/brief-<id>.md`, and run as a background shell `node <hooks>/proteus-container.js run --worktree <wt> --prompt-file <brief> --model <build> --agent <proteus-<team>-worker|proteus-worker> --ticket <n> --base proteus/<run>` (under a `--sandbox` profile, the bin copy it printed instead of `<hooks>`). Its final line `<STATUS> #<n> sent` is the worker's result; the guard refuses a `--model` that is not `build` or a `judge` escalation. Verifiers are still Agent spawns. Container workers are not beat-tracked: the runner's `--timeout` and the background-task notice replace the watchdog for them. On `isolation=container-unready`, no worker runs, unisolated or not: one line to the human naming the failed doctor row, then wait.

## 5. Escalate

One rung at a time, no restart: (a) the same worker, failing output pasted back, mechanical failures only; (b) diff and red output to a fresh worker on `judge`, not the ticket; (c) two `judge` fails → the contract is wrong, back to step 3 as a fresh task. `NEEDS dependency` from any worker → OSV query (`enforcement.md` §8), then the result and the request to the human.

## 6. Verify

`proteus-<team>-verifier`, or `proteus-verifier` with the team named, on `judge`, spawned on the worker's `DONE` without waiting for CI; the security verifier beside it when the ticket qualifies: a path matching the `security` block of `teams/ROUTING.md`, which CI marks with a red `proteus/security` status on the PR, or the lead's judgement on anything else that does. Verdict `MERGE | BACK-TO-WORKER (numbered) | CONTRACT-WRONG` as a PR review comment, then as a commit status on the head it reviewed (`proteus-signoff.js`: `proteus/verdict`, the security verifier's `proteus/security`). The ruleset requires both statuses green, so a push after the review needs a new one. Follow-ups are not tickets: a blocker is `BACK-TO-WORKER`; anything else is one line on the milestone's debt issue (`tracker.md`). Back-to-worker goes direct, one round, then it is contract-wrong. With `isolation=container` the brief carries its container line (`roles.md`), and the guard refuses a verifier's own gate or test run: the verifier replies `CHECKS:` with its commands, the lead runs each as `node <hooks>/proteus-container.js check --worktree <wt> --ref <head sha> -- <command>` and sends the `CHECK` lines and log paths back with SendMessage, and the verifier then gives its verdict. One round. The security verifier's scan: `enforcement.md` §4.

## 7. Merge

In batches: `node <hooks>/proteus-merge.js <run> --suite "<suite>"` (the gate commands from `## Learned`; `.worktrees/_run` is checked out afresh for every commit tested, made anew, with no install, so put the install in the suite). It merges every PR whose checks and statuses are all green, `proteus/verdict` among them, in dependency order (`gh pr merge --merge`), reads the run branch's tip from origin and fetches its objects, and prints one line: the merged PRs with their tickets, a stop (a conflict), and `suite: run node <hooks>/proteus-run-tree.js <sha>, then in .worktrees/_run run <command>, both sandboxed; then <next call> --result pass|fail --at <sha>`. It runs no git with a working tree and nothing from `_run` or a PR. Run both printed commands yourself, sandboxed like any gate: `proteus-run-tree.js` from the main checkout checks that commit out in `.worktrees/_run`, a repo of its own that reads the project's objects, then the suite in `_run`, bare, never through `proteus-gates-cache.js` (Codex: `workdir`, no `cd`); then the printed next call with `--result pass` or `--result fail`, its `--at <sha>` kept: the sha you tested. A result whose `--at` is not the commit the state awaits, or with no `--at`, is refused (exit 1, no sha printed), so a state an agent rewrites between your calls cannot turn your result into one for another commit. Pass ends the batch: `suite green at <sha>`, origin's tip read again, printed only when it is the commit the state names (the sha you passed to `proteus-run-tree.js`; check it); when the run branch moved or the state changed, pass refuses and prints no sha. Fail on the tip bisects the batch's merges one step per call, each printing the two commands again for the next commit, until `suite red; first bad PR #<pr> for #<n>`. Its state between calls is `<git-common-dir>/proteus/merge/<run>.json`, checked on every read (an agent can write it); a new batch waits until that one ends. Pass names the merged branches as `worktree and branch left for the lead`, each only when gh still reports that PR merged from a worker branch. The script leaves your checkout and its refs alone: on `proteus/<run>` after the batch, `git fetch origin refs/heads/proteus/<run>`, then `git merge --ff-only <sha>` with the sha `suite green at` printed, never a short ref name, which a ref an agent plants (`refs/tags/origin/...`) would shadow. `proteus-run-tree.js` refuses (exit 1) when `.worktrees` or `.worktrees/_run` is a link, and when `_run` is a worktree an older Proteus registered: the human removes that one with `git worktree remove --force .worktrees/_run`, outside any agent session. Each PR passed CI alone; one run per batch catches how they interact. `first bad PR #<pr> for #<n>` → a fix ticket for its team on `judge`, and nothing else merges until that lands, so the next bisect starts from green.

Per PR the line names as merged: close the issue, then stop the worker and its verifier (`TaskStop`), since an idle agent repeats its report and burns tokens; then, for each branch named `worktree and branch left for the lead`, remove its worktree (`git worktree remove .worktrees/<id>`, which refuses uncommitted work), delete the local branch (`git branch -D <branch>`) and the remote one (`git push origin --delete <branch>`), and run `node <hooks>/proteus-scratch.js --sweep <run>-<id>`. `conflict PR #<pr>` → a `judge` worker of the owning team runs `/resolving-merge-conflicts`. Each merged batch is a wave: `proteus-qa-verifier` once on the branch; `WAVE-RED` failures become tickets, not fixes. Milestone complete → the same agent on `judge` with the word `milestone` (`enforcement.md` §7, §10 on code); its blockers are `WAVE-RED` tickets, and the gate does not open over them. Beside it, `proteus-security-verifier` in `milestone` mode on the milestone diff (`enforcement.md` §10b). A project with a `service:` line in `## Learned` also gets the local pentest (`enforcement.md` §10c).

## 7½. Human review

Milestone complete and `WAVE-GREEN` → the gate in `review.md`: the guide opens the review issue, you poll for the verdict, and the human reviews in `/proteus-review`, not through you. `CHANGES revision`, or changes that are all small tweaks → revision mode (`operations.md`). Human away → continue only on the literal `UNATTENDED` (`review.md`).

## 8. Close

Last milestone accepted → `proteus-qa-verifier` on `judge` with the word `close` (`enforcement.md` §10 on code); red → tickets. Beside it, `proteus-security-verifier` in `close` mode over the whole repo (`enforcement.md` §10b). Every open debt line is fixed, re-scoped into a future run's issue, or dropped by the human; none stays silent. Lessons pass and upstream proposals (`lessons.md`, At step 8). Open the PR from `proteus/<run>` to `main` linking the milestones; the human merges it. If the run set branch protection, the PR body ends with the `gh api -X DELETE …/protection` command for the human. Delete `proteus-evidence/<run>` after; then delete `.worktrees/_run` (a plain directory) and `node <hooks>/proteus-scratch.js --sweep <run>`. Session ending with open work → `/handoff`. Close report: `node <hooks>/proteus-close-report.js <run>`, posted on the run log and the close PR; propose the routing changes it points to (`enforcement.md` §5). Then the retro (`lessons.md`, At step 8): a `helper` with the Retro helper prompt (`roles.md`) runs `node <hooks>/proteus-retro.js` on the close report's saved data, gives each recurring group exactly one proposal, and posts them all as one comment on the close PR, a `- [ ]` checklist. The human ticks the ones to keep; file or apply only the ticked items, and nothing is applied unasked. No groups → nothing is posted, and the run log gets `retro: none`.
