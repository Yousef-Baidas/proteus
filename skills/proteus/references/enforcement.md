# Enforcement

Rules in prompts drift. These make the important ones mechanical. Templates ship in `teams/templates/` (copied by `install.js --project`); the scaffold or stabilise ticket installs them once. §3–6, §8 and §12 apply to every domain; §1 CI applies wherever the checks run headless; §7, §9, §10 are code-only (other domains get their deep pass from the team rubric in `domains.md`).

## 1. CI on every ticket PR + run-branch rules

Scaffold ticket: copy `teams/templates/ci/proteus-gates.yml` to `.github/workflows/`, replace every `EDIT` line with the gate commands from `## Learned` (`EDIT-docs` with the docs gates: markdown lint, link check, spelling; it is the whole check on a Direct batch PR), commit. Besides each PR, the workflow runs on every push to `proteus/*`, so each merge gets `gates` on the integrated tree and then `qa`: the mechanical QA (`e2e`, `smoke` from a fresh install, `rebuild` of the deliverables, `mutation` on the files the merge changed). A step the project has no use for is deleted, not left green. Keep the template's hardening while filling it in: a `${{ }}` value a script needs goes through `env:` and is read as `"$VAR"`, never written inside `run:` (a fork names its own head branch); the token stays read-only (`permissions: contents: read`, a wider scope only on the job whose step needs it) and checkout keeps `persist-credentials: false`; every added action is pinned to a full commit SHA with its version as a comment (`gh api repos/<owner>/<action>/git/ref/tags/<tag>`, following an annotated tag to its commit); installs skip lifecycle scripts where the tool allows (`npm ci --ignore-scripts`). The QA verifier reads these runs (`gh run list`, `gh run view --json jobs`) and re-runs locally only what they do not cover (`teams/qa/PROFILE.md`). The workflow also runs on PRs into `main`, but only from `proteus-work/quick/` and `proteus-work/direct/` branches; the human's own PRs are not gated by it.

The same ticket copies `teams/templates/ci/proteus-trust.yml` to `.github/workflows/` unchanged. It runs on `pull_request_target`, so GitHub takes the workflow, the checkout and `proteus-security.js` from the PR's base, never from the PR, and it never runs the PR's code: it lists the PR's files through the API, checks the head out under `head/` as data for the scanners (§4), and posts the commit status `proteus/security` on the head, success when no changed path matches the `security` block of `teams/ROUTING.md` and the scanners found nothing new, failure naming the paths when one does or a scanner found something, until the security verifier signs off. It runs as two jobs on two VMs: `scan`, with `contents: read` and no secret, checks the head out and runs the scanners, and uploads their reports as an artifact; `post`, the one job with a write scope (`statuses: write`), checks out the base only, never the head, and reads that artifact as data (regular files, size-capped, parsed as JSON, nothing in it run) before it posts. Steps of one job share a VM and a uid, so a scanner a hostile file subverted could outlive its step and read a later step's token; a second job cannot be reached that way. A run branch cut before the file existed has no copy, so CI posts no `proteus/security` for its PRs: finish such runs before the ruleset requires that status.

What binds `proteus/<run>` is the human's, set once per repo: `install.js --protect`, run by an admin of the repo, adds the ruleset "proteus runs" on `proteus/*` (a PR with `gates`, `proteus/verdict` and `proteus/security` green, no force push, nobody bypasses, admins included) and gives the agents' own GitHub account write access. Worker branches are `proteus-work/<run>/<id>`, outside the pattern. Per run, right after `git push -u origin proteus/<run>`, check that it binds:

```
gh api "repos/{owner}/{repo}/rules/branches/proteus%2F<run>" --jq '[.[].type]'
```

`pull_request`, `required_status_checks` and `non_fast_forward` all listed → done. Otherwise fall back to protecting the branch itself:

```
gh api -X PUT "repos/{owner}/{repo}/branches/proteus%2F<run>/protection" \
  --input - <<'EOF'
{"required_status_checks":{"strict":false,"contexts":["gates","proteus/verdict","proteus/security"]},
 "required_pull_request_reviews":null,
 "enforce_admins":true,"restrictions":null}
EOF
```

The PUT needs an admin's login. Under the agents' own account (`identity=separate` in `proteus-state`) it fails with 403 or 404, as it should: tell the human once to run `install.js --protect`, and continue with prompt-enforced gates until they do. Under `identity=shared` it succeeds, and `enforce_admins` makes it bind your own login too; but that login can delete it: the guards refuse an agent's delete, so it stops a slip, not a determined script. It also fails on a private repo on GitHub Free, which has no rulesets either, and `gates` never reports when Actions is disabled. Either → write `protection: none` under `AGENTS.md ## Learned` once, tell the human once, continue with prompt-enforced gates; the verifier then runs the suite itself.

Now no PR merges into `proteus/<run>` without the `gates` check, the verifier's verdict and the security status green on its head. `strict` is off: the full suite runs on `proteus/<run>` after each merge batch and bisects a red one, so requiring every ticket branch to be up to date first would only add an update-branch and a fresh CI run per PR. Required reviews are not set: worker, verifier and lead share one `gh` login, and GitHub refuses `--approve` on your own PR. Instead the verifier records its verdict as a commit status on the head it reviewed, `node <hooks>/proteus-signoff.js <pr> <sha> MERGE|BACK-TO-WORKER|CONTRACT-WRONG`: `proteus/verdict`, and with `--security` the security verifier's `proteus/security`, which replaces CI's red one. MERGE is success, the other two failure. A status belongs to one commit, so a push after the review leaves the new head without one, and the script refuses a head that moved since the review. So the verdict locks the merge, whoever runs `gh pr merge`; who may post it is weaker. The guards refuse `proteus-signoff.js` to the lead and to every agent but a verifier, `--security` to every verifier but the security one, and any hand-posted commit status or check run (`gh api …/statuses/…`, `…/check-runs`) to everyone. Without a verifier App that is a guard, not a boundary: the verifiers post under the agents' login, the one the workers share (`identity=separate` keeps only the human apart), so a worker's own script can post the same status, and so can a workflow a worker's PR edits, since `pull_request` runs the PR's copy of `proteus-gates.yml` with a token that may ask for `statuses: write`. The owned check refuses a ticket that does not own the workflows, and `.github/**` is a security path, so such a PR needs the security verifier too.

The verifier App closes that (#81). The human creates a GitHub App with only "Commit statuses: write", installs it on the repo (its Install App tab, only select repositories), keeps its private key (Credentials > Key pairs) 0600 outside any repo and records it with `install.js --verifier-app <appId> <keyPath>` (the App ID from its General tab; `verifierApp` in `~/.claude/proteus.json`: app id, key path and `installations`, one installation id per repo owner, since an installation belongs to one account or org; run again in a repo of another owner to add it; an older lone `installationId` still serves its owner); `--protect` then pins `proteus/verdict` and `proteus/security` to the App's id (`integration_id` on those two `required_status_checks` entries; `gates` stays CI's). `proteus-signoff.js` signs a JWT with the key, trades it, through the installation of the repo's owner (none recorded: it fails naming `--verifier-app`), for an installation token limited to that repo and `statuses: write`, and posts with it as `GH_TOKEN` in the one `gh` call's environment; the token is never written, printed or put on a command line. If no token mints, the signoff exits 1 with the reason and posts nothing: it never falls back to the agents' login, whose status the ruleset would not count anyway. A status any other login posts on those contexts, a worker's script or a workflow's token, no longer satisfies the ruleset. The App gets no approving review either: the pinned statuses are already the lock, a review would only repeat the verdict, and approving needs `pull_requests: write`, a much wider grant than posting a status. `--doctor` checks the key is readable, a token mints for the current repo's owner (GitHub out of reach is a warning) and the ruleset is pinned; `--protect` warns when that owner has no installation recorded.

With the App, CI's own `proteus/security` (posted by `github-actions[bot]` from `proteus-trust.yml`) no longer counts, so a PR that touches no security path needs the App's status too. A verifier's `MERGE` without `--security` supplies it: when the head's newest `proteus/security` is CI's success saying no security path was touched (or no security block exists), and the PR's files, listed through the API, match no glob of the security block in the base branch's `teams/ROUTING.md` (read through the API, not the worktree), it posts `proteus/security` success as the App too, saying it carried CI's result over. CI's failure is never carried over: a PR that touches a security path still waits for the security verifier's `--security`. A `MERGE` before CI has posted is refused with "wait for proteus-trust, then sign off again". Without the App nothing changes: CI's red `proteus/security` blocks until the security verifier's success replaces it.

What the App leaves open: the agents run as the human's OS user, so the key is a file they could read. The hooks keep it out of reach (Read and Edit of the key path, any shell command naming its file, and any agent shell setting `GH_TOKEN` or `GITHUB_TOKEN` are refused for the lead and every agent; `proteus-shell-check.js` fingerprints the key), but a process outside the hooks, or a command that reaches the key through a variable, a glob or an interpreter, still can. `proteus-signoff.js` itself is refused to every agent but a verifier: a worker's session refuses it whatever the agent is called, and a subagent its harness does not name is refused when its brief names a worktree. Keep the key 0600 and outside every repo, and give the App nothing beyond commit statuses. Verifier reads `gh pr checks <pr> --json name,state` instead of re-running the suite; it re-runs only what it needs to reproduce a finding, or the whole suite when the checks list is empty.

The guards hold every agent to this, ruleset or not: they refuse `gh pr merge --admin`, a push to `main` or to an existing `proteus/<run>` (the push that creates it passes), deleting either, any change to branch protection or a ruleset except the PUT above, and a commit status or check run posted by hand.

At close, if the PUT set the protection, the human deletes it before deleting the branch; the guards refuse it to agents, so the close PR's body ends with `gh api -X DELETE "repos/{owner}/{repo}/branches/proteus%2F<run>/protection"` for them. The ruleset stays.

## 2. Path ownership hook

Before spawning a worker, from the repo root (`<hooks>` and other names per `harnesses.md`):

```
node <hooks>/proteus-worktree.js <wt> [--tier <tier> [--human]] <owned paths and globs…>
```

It writes the owned-paths file `<wt>/.claude/proteus-owned` (`.codex/proteus-owned` on Codex; one path or glob per line, each owning what it matches and everything below a folder it matches; re-running replaces the list), copies the worker hooks and their settings into the worktree as a backup, and adds those local files and `/.worktrees/` to the repo's `info/exclude`; same on Linux, macOS, and Windows. Workers run inside the lead's process, so the rule that bites is the lead's `proteus-lead-guard.js`: for a subagent it refuses every edit (`Edit`/`Write`, Codex `apply_patch`) outside the worktree's `proteus-owned` list with the `NEEDS` instruction as the error, any edit in another worker's worktree, and any subagent edit to the main checkout while a run is open. The scratch dir `<git-common-dir>/proteus/scratch/` (`proteus-scratch.js --path`) is the exception, allowed to every agent from a worktree or not. No glob covers the owned-paths file itself (`*/*` and `**` match `.claude/`): an edit of it is refused in any spelling NTFS or a case-insensitive filesystem resolves to it (any case, a trailing dot or space, a `:stream` suffix), so a worker cannot widen its own ownership. A subagent's worktree is its cwd's when that is a prepared worktree. Otherwise (a subagent keeps the lead's cwd on both CLIs), on Claude Code it is the one prepared worktree its brief names (`worktree <absolute path>`, `roles.md`), read from the first message of the subagent's transcript, so an edit anywhere else in a linked worktree, its very first included, is refused with a message naming the brief's worktree. With no worktree in the brief (helpers, the scout, the guide), several (a contracts worker, one per ticket), or on Codex, whose spawn message is encrypted in the subagent's rollout, its first edit in a prepared worktree binds it there. Either binding is recorded per agent id in `<git-common-dir>/proteus/agents/`. A first-edit binding refuses an edit in a different prepared worktree, naming the agent's own, while the own one has uncommitted changes; once they are committed the binding moves, which is how a contracts worker goes from one ticket's worktree to the next. There the first edit decides: a Codex worker whose very first edit lands in another worker's worktree is bound there and not refused, so the brief still names each worker's worktree by absolute path. Shell writes (`sed -i`, redirects) skip those hooks, so two more checks run `proteus-owned-check.js`: a `pre-commit` hook that `proteus-worktree.js` installs in that worktree only (`extensions.worktreeConfig` plus `git config --worktree core.hooksPath`, git 2.20+, same on every OS; the main checkout's hooks are untouched, and the repo's existing hooks such as lefthook's commit-msg are forwarded; a repo with no commit-msg hook gets one that runs `commit-msg.js`, the check CI runs) refuses a commit whose staged paths are outside the `proteus-owned` list, and the `owned paths` step of `proteus-gates.yml` fails a PR from `proteus-work/<run>/<id>` that changes a path outside the lead's record of the ticket, `.proteus/owned/<id>` (one path or glob per line, `#` comments) as committed on the base `proteus/<run>`; both refuse the owned-paths file itself whatever the globs say. The record is read from the base, never from the PR, and the step runs the base's copy of `proteus-owned-check.js` from a detached worktree of the base, so the worker can change neither: the base takes commits only through a merged PR with `gates` green (§1), and the step refuses any PR that touches `.proteus/owned/` except the lead's docs PR from `proteus-work/<run>/lead-docs`, which is checked against the lead's own list instead (`bootstrap.md`) and which the worker guard refuses a worker's push to. A missing record fails the step; a PR body's `Owned:` line does not stand in for it on a run branch. Two cases still read the body's line, which the worker writes: a PR into `main` (Quick and Direct; the human merges those after reading the diff), and a run whose base has no `.proteus/owned/` at all, i.e. one cut before the records, which the step names in a warning until that run's close PR merges (this fallback is removed in the next minor release). The record is not the issue body: every agent may post as one account (`tracker.md`), and nothing stops that account editing an issue, while the run branch is a ruleset's to guard. Not airtight even so: `git commit --no-verify` skips the hook, a PR runs the workflow file from its own head, so a worker that edits `.github/workflows/proteus-gates.yml` can drop the step (the edit itself is outside its record unless the ticket owns the workflow), and a worker's script can push the lead-docs branch where the guard cannot see; the lead's `--match-head-commit` merge catches that last one. The verifier's `gh pr diff <pr> --name-only` against the owned paths stays the backstop and any file outside them is `BACK-TO-WORKER`. These files are untracked and die with the worktree. No list file → allowed, so verifiers and bootstrap are unaffected.

Tier ceiling (`SKILL.md` rule 3). `--tier` writes `# tier <tier>[ human] <base sha>` as the list's first line (a comment to the owned check); the base is `HEAD` at the first preparation and is kept on re-runs, so a Direct batch is measured whole. The same `pre-commit` then runs `proteus-tier.js --staged`: everything since the base, by the `tiers` block of `teams/ROUTING.md` as of the base, against the declared tier; a change that outgrew it is refused with the tier it needs. CI's `tier` step runs `proteus-tier.js --ci` on every `proteus-work/` PR: the declared tier is `direct` on a `proteus-work/direct/` branch, else the body's `Tier:` line, else `standard`. Rules come from the base so a change cannot loosen its own ceiling; `(human)` and the body line are the agent's to write, so they are a tripwire, not a lock; unlike the owned paths, the tier has no lead-written record yet. The Direct helper needs nothing more from the guards: its edits are in a prepared worktree, its branch is new, and its PR targets `main`, which only the human merges.

## 3. lefthook + commit-msg check

Scaffold ticket: install lefthook (`npm i -D lefthook` / `pip install lefthook` / `cargo binstall lefthook` / `pacman -S lefthook` / `brew install lefthook`), copy `teams/templates/lefthook.yml` to the root, fill the `EDIT` lines, `lefthook install`. A test runner, linter or watcher that walks into dot folders (vitest, jest, eslint, vite; README "Worker worktrees") gets `.worktrees/` in its ignores. Its pre-push test goes through `teams/templates/hooks/proteus-gates-cache.js`, so a tree the worker already passed is not tested again on push. lefthook and `proteus-gates.yml` run `node teams/templates/hooks/commit-msg.js`, so `teams/templates/` is committed. The commit-msg check rejects non-Conventional subjects, >72 chars, and any AI attribution trailer. CI runs the same check on every commit in the PR, so a worker that skipped hooks still fails.

## 4. Scanners and the security trigger

`teams/security/PROFILE.md` runs `semgrep --config p/owasp-top-ten --config p/secrets --json --quiet $(gh pr diff <pr> --name-only)` first and attaches findings, then reads. Missing semgrep → `pipx install semgrep` or note once and continue.

Which PRs get the security verifier is CI's call first (§1): `proteus-trust.yml` marks a PR whose changed paths match the `security` block of `teams/ROUTING.md` with a red `proteus/security`. Its scanners mark a PR too. The two jobs (§1) protect the token, not the verdict: a scanner a hostile head subverts can still write a clean artifact and so forge a pass. Before posting, the `scan` job runs `proteus-scan.js` on the head, semgrep as an image pinned by digest and every download checked against a sha256: semgrep (`p/owasp-top-ten`, `p/secrets`) on the changed files, gitleaks on the PR's commits read from a mirror clone with no working tree (so a secret a later commit deleted still counts; a base or head commit missing from the mirror fails the job, never reads as clean), osv-scanner when a lockfile changed (`requirements-*.txt` and `requirements/*.txt` included), with call analysis off so no `go` or `cargo` runs on the head, and zizmor when a workflow under `.github/workflows/` or a composite action's `action.yml` changed (actionlint, on the workflows, where zizmor is missing, locally). A symlink the PR turns into a regular file counts as changed. A tool with nothing to scan logs one skip line and passes; in CI a missing tool fails the job (`--require`). Nothing the PR can write quiets them: no `.semgrepignore`, `nosemgrep`, `.gitleaks.toml`, `.gitleaksignore`, `gitleaks:allow`, `osv-scanner.toml`, `zizmor.yml` or `# zizmor: ignore` is honoured. `proteus-security.js --findings` reads their SARIF, and any finding the base's `teams/baseline.json` does not record under the gate `security` turns `proteus/security` red, with or without a `security` block. Every log line that can hold head text (a changed path, a finding, a scanner's stderr) prints between `::stop-commands::<token>` and `::<token>::`, the token 16 random bytes drawn per print and absent from that text, so no path or message runs as a workflow command in either syntax (`::cmd::`, `##[cmd]`); every such line also opens with a fixed prefix (`proteus-scan: `, `proteus-security: `, `finding ` for `--list`) and shows control characters as `?`, so no head text starts a line, and all of `proteus-security.js`'s fenced output goes to stdout, since the runner shares the stop state across streams. A repo with findings it already carries records them once with the ratchet (§12), from a checkout of the default branch, and commits the file:

```
node teams/templates/hooks/proteus-scan.js --dir . --all --out <tmp dir>
node teams/templates/hooks/proteus-baseline.js security --record --match "^finding " -- node teams/templates/hooks/proteus-security.js --list <tmp dir>
```

A recorded finding stays quiet while its tool, rule and path stay the same, matched exactly with their digits (a CVE id is the rule, so another CVE in the same lockfile is a new finding); fixing it and re-recording tightens the baseline. The lead still adds the security verifier wherever else it judges one is due; on a PR CI did not mark, the security verifier's `--security` signoff replaces CI's success.

## 5. Cost

Step 8 runs `node <hooks>/proteus-close-report.js <run>`. From the tracker it prints, per ticket, the PRs, bounces (`BACK-TO-WORKER` verdicts), escalations (`RED` reports and `CONTRACT-WRONG` verdicts) and wall-clock (issue created to closed); per team and difficulty, the bounce rate, escalation rate (share of tickets with at least one) and median wall-clock; and a summary line with the run's totals and cost. Cost comes from `npx -y ccusage@20.0.26 session --json` (Codex: `npx -y @ccusage/codex@19.0.0 session --json`; they read local JSONL, and npx fetches the pinned version once), summed over the sessions the journal saw a human message in during the run. ccusage splits by session, not ticket, so cost per ticket is that sum over closed tickets, an average. `--cost-json <file>` reads a saved report, `--no-cost` skips it. The lead posts the output as a comment on the run-log issue and pastes it into the close PR body. Then it tunes routing from the team rows: a team and difficulty whose tickets bounce or escalate on most tickets goes to `hard` (`top`) next run, or gets smaller tickets; one with no bounce on `hard` is offered at `standard`. Each change is one line to the human; once approved, a difficulty rule goes in `AGENTS.md ## Learned` for the next run's ticketing, a `teams/ROUTING.md` change through a ticket. Long-term trends: Claude Code's OpenTelemetry export (`CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER=otlp`, endpoint of your collector); per-profile cost falls out of the session tags.

## 6. Skill pinning

`teams/link-skills.js` writes `teams/skills-lock.json` (source and sha256 over the skill's files, per linked skill) and warns `drift: <skill>` when a machine's copy differs from the committed hash. Commit the lock; a teammate whose install drifted re-runs `npx skills update <skill>` or accepts the new hash by re-running the link script with `--relock`.

Drift blocks dispatch. Each session start re-hashes every skill linked under `teams/<team>/.claude/skills` and `.agents/skills` against the lock (`proteus-state` shows `skills-lock=drift:<skills>` and a note), and `proteus-lead-guard.js` refuses a `proteus-worker`, `proteus-verifier` or `proteus-<team>-worker`/`-verifier` spawn while any differs, naming the skills and both fixes. Helpers (scout, guide, any other agent) still spawn. The check is local: a clean result is cached in `<git-common-dir>/proteus-lead/skills-drift.json` until the lock changes or the next session starts, and a drift is re-checked on every spawn, so the block lifts as soon as the copy matches or the lock is rewritten. Re-locking is the human's call, since it admits new third-party text into every worker.

## 7. Mutation testing per milestone

CI's `qa` job mutates the files each merge changed (§1), so every changed file is mutated once, off any agent's clock. Once per milestone, `teams/qa/PROFILE.md` reads the `mutation` step of every push run since the milestone's merge-base; without that step in the workflow it runs Stryker (`npx stryker run --mutate <files>`), `mutmut run --paths-to-mutate <files>`, or `cargo mutants --file <f>` locally on the files changed since the merge-base. Surviving mutants in a changed file → `WAVE-RED` finding `MUTANT <file:line> survives`, ticketed like any other red. Judged per milestone, not per ticket; it is the slow gate.

## 8. Dependency check on `NEEDS`

Worker comments `NEEDS dependency <ecosystem>/<name>@<version>`. Lead, before asking the human:

```
curl -s https://api.osv.dev/v1/query -d '{"package":{"name":"<name>","ecosystem":"<npm|PyPI|crates.io|Go>"},"version":"<version>"}' \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const v=(JSON.parse(s).vulns||[]);console.log(v.length?v.map(x=>x.id+" "+(x.summary||"")).join("\n"):"osv: clean")})'
```

Result goes into the issue comment with the request. The human still decides; unattended mode parks it. Once the dependency lands, CI's osv-scanner (§4) checks the changed lockfile, transitive updates included, on that PR and every later one that changes it.

## 9. anti-slop lint rules (JS/TS)

Required, `teams/devops/required.txt`. The scaffold or stabilise worker reads `teams/devops/PROFILE.md`, runs the `install-anti-slop` skill, and the vendored oxlint plugin (`tools/oxlint/anti-slop/`) joins the lint gate: lefthook pre-commit, CI `gates`, and every worker's green. After that it costs no agent a token; slop fails lint like a type error fails the build. `CONVENTIONS.md` forbids new dependencies → ask the human about the dev-only `oxlint` and `@oxlint/plugins` before writing that ticket: its worker cannot add them and would stop on `NEEDS` mid-wave. The config is `.oxlintrc.json`, which needs no TypeScript loader. A rule that fights `CONVENTIONS.md` is disabled there with the convention quoted; the human's file wins. No JS/TS in the repo → write `anti-slop: n/a` under `## Learned` once. Updating the rules is a devops ticket, never a side effect.

## 10. Deep review per milestone, architecture scan at close

Required, `teams/qa/required.txt`. Per-ticket verifiers check a diff against its contract; nobody at that level sees what five merged tickets did to a module. So at every milestone the QA pass (`judge`) applies `thermo-nuclear-code-quality-review` to the milestone diff; its blockers are `WAVE-RED` tickets and the human gate stays shut until they merge. Per milestone, not per ticket: on a forty-line diff it demands rewrites the ticket never asked for and doubles the verifier bill. At close the same agent runs the scan phase of mattpocock `improve-codebase-architecture` and files at most five candidates on the last milestone's debt issue. Both are read from their `SKILL.md`; both are `disable-model-invocation`. Non-blocker findings go to the milestone's debt issue, where the human decides at close what becomes a run.

The same scan also runs before the work, on the modules it touches: the refactor checkpoint in `flow.md` step 1.

## 10b. Security pass per milestone and audit at close

A security verifier sees one ticket's diff, so an access path built across three tickets passes each review on its own, and nobody audits the whole repo before the human merges into `main`.

- Milestone mode: the QA milestone pass (§10) also spawns `proteus-security-verifier` on `judge` with the word `milestone` and the milestone diff, `git diff <merge-base>..proteus/<run>`. It checks the flows across tickets: authorization on every new route or handler, every input that reaches file, network, database or shell I/O, and each of the milestone's gate (g) abuse cases (`flow.md` step 1).
- Close mode: at close the same agent runs with the word `close` over the whole repo at the tip of `proteus/<run>`, applying the audit skill the scout picked for `teams/security` (a line of `teams/security/skills.txt`), read from its `SKILL.md`.
- Blockers become `WAVE-RED` tickets exactly as §10's do: numbered, mapped to the ticket that introduced them, fixed by tickets, never by the verifier. Non-blockers go to the milestone's debt issue.
- The human gate does not open over a security blocker. Like §10, the lead's instructions hold the gate (`flow.md` step 7, `review.md`); no hook enforces it yet.
- No path the run touched matches the `security` block of `teams/ROUTING.md` → both modes are skipped, and the lead writes `security-pass: skipped (no security path)` on the run log.

## 11. Hooks

Hooks never let git read a config an agent can write (#215). They run outside the sandbox, and a sandboxed command can rewrite `<common>/commondir`, a worktree's `.git` file, its gitdir's `commondir` or `config.worktree`, or rename that gitdir. Any of these hands git a config whose `core.fsmonitor`, or a clean filter named in `.gitattributes`, runs a program with the human's rights the next time a hook asks git anything. So every hook git call goes through one wrapper in `proteus-lib.js`. It pins `GIT_DIR` and `GIT_COMMON_DIR` to the repo's common dir, turns off the system and global config, and turns off `core.fsmonitor`, `core.hooksPath`, `core.untrackedCache` and submodule recursion (`fetch.recurseSubmodules`, `submodule.recurse`), since a submodule's config under `<common>/modules` is an agent's to write. The pin keeps git's config at `<common>/config`, but git's files ref backend still follows a `<common>/commondir` file, so hook git is refused on a common dir that holds one when the check runs (an lstat before git starts); a racer that creates the file between the check and git's read gets past it. It reads a worktree's HEAD as a file under `<common>/worktrees/<id>/`. It reads the worktree's changes with `git diff` against that HEAD and `git ls-files -o`, using its own index, never `git status`. `git diff` rewrites a stat-dirty index by path, through a lock and a rename, so it runs on a private copy: the hook copies the index into a new file (`wx`) in a fresh private dir under `<git-common-dir>/proteus-lead/`, which the profile denies, and deletes the copy afterwards. It does not use the temp dir, because a temp dir that sandboxed commands can write would let an agent swap that dir too. It reads the index only when it is a regular file of at most 64 MB, opened without following a link, and otherwise reports no changes known. An agent that swaps `<common>/worktrees/<id>` for a link therefore cannot aim the rewrite at another dir. Three exceptions keep the human's global and system config, `verify-tag` and `fetch` on the plugin home or its release clone and `proteus-merge.js`'s `fetch` of the run branch, because their trust and credentials live there. The common dir comes from the harness's project dir (`CLAUDE_PROJECT_DIR`), not the shell's cwd. It must be a real `.git` directory above `<main>/.worktrees/<id>`, `<main>-proteus/<id>` or `<main>/.claude/worktrees/<n>`, or at the project dir itself. A dir in none of that common dir's checkouts gets no git at all, never its own repo's, since a sandboxed command can build a repo with its own config anywhere it writes: there the hooks act as they do outside git (the bind check reads it as idle; the push, restore and pathspec guards judge it as a dir outside git). `install.js --project <dir>`, which the human runs, takes that dir's repo instead. `proteus-worktree.js` runs outside the sandbox, so its worktree argument never picks the repo: it prepares only a worktree the project's common dir registers, and refuses any other path without running git there. `proteus-merge.js` runs outside the sandbox too (the Codex rules allow it, for `gh` and its fetch), so it does only `gh` merges, the fetch, ref reads and its own state file: no git with a working tree or an index, no `read-tree`, no checkout, nothing under `<common>/worktrees`, and nothing from `.worktrees/_run` or a PR (no suite, no gates cache, no install). Its fetch also passes `--no-recurse-submodules` and `core.alternateRefsCommand=true`, so it runs no `git for-each-ref` in an alternate an agent lists in `<common>/objects/info/alternates`. It takes origin's URL from `<common>/config` alone and refuses when that names none, never from `<common>/remotes/` or `branches/`. On pass it reads origin's tip again and prints it only when it equals the commit the state names. It prints two commands with the commit to test, and the lead runs both inside the sandbox: `proteus-run-tree.js <sha>`, then the suite in `_run`, and reports `--result pass|fail`; the bisect is that loop. `proteus-run-tree.js` is in no prefix rule or sandbox exclusion (a test holds this), so a link an agent swaps in for `_run`, or a linked `<common>/worktrees/_run`, gains nothing the sandbox did not already allow. It deletes `<main>/.worktrees/_run`, a plain directory and no registered worktree, and makes it anew for each commit: `git init`, the project's objects through alternates, a detached checkout of the commit, its `HEAD^{tree}` checked against the commit's tree in the project's repo, so nothing an agent planted in an old `_run/.git` (a replace ref, an index, a filter) carries over; it still refuses a `.worktrees` or `_run` that lstat shows is a link. The state between calls, `<common>/proteus/merge/<run>.json`, is written only as a new file (`merge/` lstat'd as a real directory, an old file unlinked, the new one opened exclusive) and read only as a regular file, never through a link (#226). An agent can still write it, so every read checks it: PR and ticket numbers positive integers, every commit a full id, the bisect bounds integers within the merged list, every branch a worker branch; anything else refuses. It removes no worktree and deletes no branch (`gh pr merge` without `--delete-branch`, so gh runs no git in the main checkout). On pass it names the merged branches, each re-read from `gh pr view` and named only when that PR is merged from a worker branch, never from the state; control characters are stripped from all it prints. Under `install.js --sandbox` the copy of `proteus-worktree.js` that runs outside the sandbox takes the main root and the state dir `<common>/proteus` from `sandbox-root.json` beside it (`lib.pinProject`), never from the cwd, the project dir, a `.git` file or a `commondir`, and refuses when that file is missing or unreadable. While a session runs, that copy creates, renames, writes and deletes nothing in a dir the profile lets sandboxed commands write, which is all of `<common>` but the files it denies: a lock or a parent dir there can be swapped mid-run. It reads `<common>/config` and adds a new submodule's deny rules to the profile, under `proteus-sandbox/`. `install.js --sandbox` sets `extensions.worktreeConfig` in `<common>/config` before the session, and the copy refuses when it is missing. Everything else in preparing a worktree (its `.claude` files, its `config.worktree` and pre-commit hooks, `info/exclude`, the `--allow` state) is written by the in-repo script inside the sandbox. The worker's own hooks and config are not a boundary: the worker can rewrite its `config.worktree`, its `proteus-hooks/` and its `.claude` files, so its pre-commit owned-path check is a convenience, and the boundary is CI's check of the PR against `.proteus/owned/<id>` on the run branch. The profile still denies the main `.git/config`, `.git/config.worktree` and `.git/hooks`, which the hooks' pinned git and the human's git read. It also denies the root's hooks dir and `.claude/settings*.json`, with `settings.json` and `settings.local.json` also named exactly, the form Linux honours. A hook planted there, or a gate flipped in those settings, would make the plugin's SessionStart run `install.js` outside the sandbox. `--sandbox` makes writable only the fixed guest dir `~/.proteus/guest/<repo>-<hash>`, never another dir `guest.json` names, since sandboxed commands can write that file. `--sandbox` finds the repo the same trusted way and refuses when it is not run inside that main checkout. A known gap (#231): outside that pinned copy, a layout none of the paths above match falls back to following `.git` files and `commondir`, so for that layout the anchor itself can be steered.

Hooks never write through a link an agent can plant (#236). Agents, and a sandboxed lead shell, can write `<git-common-dir>/proteus/`, so every file a hook (or a lead script run unsandboxed) creates, rewrites, appends, renames or deletes is in `<git-common-dir>/proteus-lead/`: the journal, the bindings in `agents/`, spawn records, beats, tamper records, lead windows and notices, the guard's hash cache, the inbox and drift caches, lesson hits, the scratch ledger and the `--allow` entries already used. `proteus-lib.js` `leadDir` resolves it and refuses, writing nothing, when `<git-common-dir>` or `proteus-lead` (or a dir under it) is a link or not owned by the current user. A rewrite is a new temp file created with `wx` and renamed inside that dir, an append opens with `O_NOFOLLOW`, and a removal unlinks the link, never its target. On first use the lead's files are copied over from `<git-common-dir>/proteus/` (regular files only, never through a link). What agents and lead scripts write there stays there and is read as untrusted (a regular file, opened without following a link, size-capped): the scratch dirs, `allow/`, `guest.json`, `gates/` and `forgotten.json`. A hook never writes back into them. Notices left in `unattributed/` from before #236 are imported once with the rest and that dir is never read for notices again; every notice is checked when shown (a positive integer `seq`, times as numbers, every string printable, with no control characters and at most 512 characters) and one that fails is dropped and its name logged to stderr. No hook deletes anything under `<git-common-dir>/proteus/scratch` or runs `git worktree remove` or `prune`: the stale sweep runs only from the lead's own sandboxed shell (#237), and the hooks' git runs with `-c maintenance.auto=false -c gc.auto=0 -c gc.worktreePruneExpire=never`, so a commit or fetch from a hook never starts the automatic gc whose worktree prune deletes through a link planted under `<git-common-dir>/worktrees/` (#235). The sweep runs `git worktree prune` only when every entry of `<git-common-dir>/worktrees/` is a real dir holding a regular `gitdir` file, and otherwise skips it and names the entry. The human's own git is not pinned: `docs/install.md` Known gaps. `leadCreate` lstats its path first and refuses if anything is there, as Windows' `wx` creates through a dangling link; the gap between that lstat and the open is Windows only and outside any boundary, as Windows has no Proteus sandbox. The session-start hook no longer appends to `.git/info/exclude`; `install.js --project` writes those lines. `install.js --sandbox` makes `proteus-lead` before it writes the profile (owned by the user, mode 0700; it refuses when a link or a file is there), and the profile denies writes to `<git-common-dir>/proteus-lead/**`. Without the profile, an agent with unsandboxed shell access can still edit the lead's state directly.

### The human's verdict

An `ACCEPT`, `CHANGES` or `ANSWER` counts only from the human's login (`proteus-verdict.js`). With a login of their own for the agents (`identity=separate`), the review session posts it under the human's, through one command: `node <hooks>/proteus-verdict.js <issue> --post --body-file <file> --sha <sha256>`. It posts the file's bytes when their sha256 is still `<sha256>`, the first line opens with a verdict word, the issue is labelled `proteus-review` or `proteus-question`, and the human's gh login (`GH_CONFIG_DIR` dropped, so gh's own default: `$XDG_CONFIG_HOME/gh`, `%AppData%\GitHub CLI` on Windows, `~/.config/gh`; or `humanGh` in `~/.claude/proteus.json`) is `human`.

The lead guard runs on that command in every session, `PROTEUS=0` included (`lib.humanPost`). On the main thread it reads the body file once, hashes it, and answers `permissionDecision: "ask"`: the human sees the issue, its title, the login and the body's first lines in the permission dialog and approves or declines. A missing or stale `--sha`, a body that opens with no verdict word, the human's gh logged in as someone else, the command run in any other form (chained, wrapped, a copy of the script) are denied first. Subagents, teammates and worker worktrees are denied outright. Where the dialog cannot reach the human the guard denies and prints the command for the human's own terminal, which runs it with no hook:

| Session | Hook `ask` | Proteus |
|---|---|---|
| `default`, `acceptEdits` | the permission dialog | ask |
| `auto` | a dialog from Claude Code 2.1.211; before, the classifier could approve it unseen | ask from 2.1.211, deny when the version is older or unknown |
| `plan`, `dontAsk`, `bypassPermissions` | no command runs, the prompt is denied, or prompts are off | deny, print the command |
| `-p` and the Agent SDK (`CLAUDE_CODE_ENTRYPOINT=sdk-*`) | denied, or answered by the program's permission tool, not the human | deny, print the command |
| no `permission_mode` in the hook input, or one Proteus does not know | unknown | deny, print the command |
| Codex | no ask: its `PreToolUse` hooks allow or deny | deny, print the command |

Sources: https://code.claude.com/docs/en/hooks (PreToolUse decision control, `permission_mode`), https://code.claude.com/docs/en/permission-modes, https://code.claude.com/docs/en/headless; checked against Claude Code 2.1.302, where `claude -p` ran no asked command in any mode.

While `agentGh` is set, the guards also keep every agent, the lead and the review session's included, off the human's login (`lib.humanGhDenial`): Read, Edit and any shell word naming a path in the human's gh config dir, a shell that sets or unsets `GH_CONFIG_DIR` or `GH_HOST` or runs `env -i`, `gh --hostname`, and `gh auth login`, `logout`, `switch`, `token` and `refresh`. The dir is also a guarded path for shell writes (`guardedWrite`, `guardedParent`). What stays open, as with the verifier App's key: the agents run as the human's OS user, so a script file, an interpreter or the OS keyring (where gh keeps the token) reaches the login without naming any of it. The boundary is the human's click and the verdict script's author check; the guards keep honest mistakes out.

No hook reads Claude Code's hook JSON itself. `proteus-harness.js` loads the adapter named by `PROTEUS_HARNESS` (`proteus-harness-<name>.js`, default and fallback `claude`), which turns the CLI's input into one Proteus event, answers for the hook (deny, add context, keep going), reads the transcript, and knows where the CLI keeps settings, agents and worker hooks. `proteus-lib.js` is the part every CLI shares. The event and adapter contract are documented at the top of `proteus-harness.js`. Hooks installed under `.codex/hooks` use the Codex adapter. The default model ladder belongs to the adapter; a CLI without one runs single-model, every spawn on the lead's model, until `models.ladder` is set.

Every guard decision that turns on an agent's name (a verifier's signoff and the security verifier's `--security`, the worker and verifier spawns the skills-lock check refuses, the beats the watchdog reads, the scout's `teams/*/skills.txt`) reads it through `lib.agentName`, which strips a leading `proteus:`, the namespace a Claude Code plugin gives its agents (#136). Only that namespace: an agent named in another one, such as `evil:proteus-verifier`, is no Proteus agent and counts as an agent the harness names that is not a verifier, worker or scout, since any plugin can ship an agent under a Proteus name. An agent with no name at all is unchanged.

`PROTEUS=0 claude` (`PROTEUS=0 codex`) opens a plain session with none of the lead's hooks but the lead guard's verdict checks (The human's verdict, above): the review session, or the human working by hand. Hook state lives in `<git-common-dir>/proteus/` (`journal.jsonl`, `inbox.json`, `lesson-hits.jsonl`, `lead-model.json`, `skills-drift.json`, `visibility.json`, `scratch-ledger.jsonl`, `scratch/`, `scratch-size.json`, lesson and stall caches) and is never committed. `node <Proteus checkout>/install.js --doctor` checks the whole install, `--doctor --fix` repairs what it safely can.

## 12. Baseline ratchet

A gate that is red on `main` when Proteus arrives would block every ticket, and a worker cannot tell its red from the repo's. The stabilise ticket records it instead and runs the gate through the ratchet, which fails only on what is new:

```
node teams/templates/hooks/proteus-baseline.js <gate> --record [--mode lines|count] [--match <re>] [--ignore <re>] -- <command…>
node teams/templates/hooks/proteus-baseline.js <gate> -- <command…>
```

- The first line, once per red gate, writes `teams/baseline.json` (`gates.<gate>`: mode, match, findings or count, exit); commit it. The second is the gate line in `proteus-gates.yml`, `lefthook.yml` and the worker's green. One argument after `--` runs as a shell line; several run as argv.
- `lines` (default): every output line matching `match` is a finding, compared as a multiset after stripping ANSI codes, the checkout path, `ignore`, and with every number turned into `#` (line numbers and timings move without the finding changing). The gate `security` keeps its digits: its lines carry no line number, and a CVE id is the finding (§4). The default `match` catches `FAIL`, `FAILED`, `Error`, `error`, `warning`, `not ok`; set one per runner, e.g. `^FAILED ` for pytest, `^\s*FAIL ` for vitest and jest.
- `count`: the sum of the numbers `match` captures, e.g. `(\d+) (?:errors?|warnings?)` for a linter summary, must not grow.
- A command that exits 0 passes. A non-zero exit passes only when every finding is in the baseline; a non-zero exit with no finding the regex recognises fails (a crash or a changed output format is not "nothing new"), and so does any red run of a gate recorded green.
- `--record` on an existing entry only tightens: it refuses while a finding is not in the baseline. `--reset` re-records from scratch and is the human's call. A run that reports `fixed` prints the tighten hint; the lead puts `teams/baseline.json` in the owned paths of the ticket that fixes a recorded failure, and that worker re-records.
- A gate with no entry passes its own exit code through, so nothing is ratcheted by accident.
- In guest mode (`bootstrap.md`) the default file is `<guest dir>/teams/baseline.json`, outside git, found from any worktree of the repo; the lead records and tightens it.

Limits: a line-based finding is only as stable as the runner's output. A renamed test or a reworded message is a new finding and its old line a fixed one; a flaky test shows up as new when it fails and was not recorded; two failures that print the same line once digits are gone count as one line twice, not as two names. A count cannot tell one new failure from one fixed, so a ticket that fixes one and breaks another passes; prefer `lines` with a runner-specific `match` and keep `count` for linters whose per-finding lines are too noisy. Output over 512 MB, or a command past `PROTEUS_BASELINE_TIMEOUT` (default one hour), fails.

## 13. A worker's shell

A worker's shell writes only its owned paths (§2) and its scratch dir (`proteus-scratch.js --path`), the same rule its `Edit`/`Write` already follow (#48). `lib.workerDenial` applies it, so the lead guard (an in-process worker, named `proteus-[<team>-]worker`) and the worktree's own worker guard (a session opened in the worktree) refuse the same commands. A verifier's, the guide's, the scout's and the lead's shells keep the rules in §11.

- **Writes.** The command is tokenised as the shell does: quotes join words, it splits on `&& || ; | & ( )`, newlines and redirections, and heredoc bodies are skipped. Each word is judged as written, without backslash escapes, and as its value after the first `=`. Write targets are redirect targets (`>`, `>>`, `>|`, `&>`, `N>`; a `>` inside `$(( ))`, `(( ))` or `[[ ]]` is a comparison, unless its operand is a literal path, which dash would write), `tee [-a]` arguments, the files of `sed -i`/`--in-place`, `perl -i`, `ruby -i`, `gawk -i inplace`, the outputs of `sort -o`, `curl -o`/`--output` and `wget -O`/`--output-document`, the dir `tar -x` extracts into (`-C`/`--directory`, else the cwd) and the one `unzip` does (`-d`, else the cwd), and the destinations of `cp`, `mv`, `install`, `ln`, `rsync`, `dd of=`, `truncate`, `touch` and `rm`, after a `cd` chain and through `sh -c`, `eval`, `busybox`, `xargs` and `find -exec`. `xargs` followed by a writer is refused outright, since it writes paths it reads at run time. `git -C <dir>`, `-C<dir>`, `--git-dir=` and `--work-tree=` are followed.
- **Links.** `ln`/`ln -s`/`link` making a link inside the worktree whose target is outside the owned paths and the scratch dir is refused: a later write through the link would land there. A symlink target is resolved from the link's dir, a hard link's from the cwd. A target is allowed only inside an owned path (an owned glob `src/**` covers the dir `src`) or the scratch dir; `/dev/null`, `/dev/stdout`, `/dev/stderr` and `NUL` stay allowed. Anything else is refused with one line naming the path. A target the shell builds when it runs (`$VAR`, `$(...)`, backticks) cannot be judged and is refused too: name the path literally. Build output (`dist/`, `node_modules/`) a ticket's commands write must be in its owned paths or ignored by the build.
- **Always refused**, whatever the owned list says: the §11 paths (`.claude/`, `.codex/`, `.agents/`, `.git/` except through git, lefthook config, `.github/workflows/`, `.github/actions/`, `teams/templates/hooks/`), so `.claude/agents/`, `.claude/settings*.json` and the owned list itself, and the anchors `proteus-confine.js` uses: `~/.claude`, `~/.codex`, `~/.agents`, `$CLAUDE_CONFIG_DIR`, `$CODEX_HOME` and the plugin root.
- **Inline code.** `sh`/`bash`/`zsh`/`dash` scripts given with `-c`, also at the end of a flag cluster (`-ec`, `-xc`), and through `busybox sh -c`, are judged as command lines; a shell fed a heredoc, a here-string or a pipe is judged on what it reads, and so is `source`/`.` of stdin, a here-string or `/dev/stdin`. Sourcing a file in the worktree runs like any script there. For `python -c`, `python3 -c`, `node -e`/`-p`/`--eval`/`--print`, `perl -e`/`-E`, `ruby -e` and the program text of `awk`/`gawk`/`mawk`/`nawk`, and those interpreters reading a heredoc or a pipe, every string literal and path-like word in the code is judged: a guarded path is refused, and a string literal resolving outside the worktree and its scratch dir is refused. Strings with spaces, URLs and escape sequences are text, and a worker's own scripts on disk (`node scripts/build.js`) run as before.
- **Known false positive.** Inline code that only *reads* a path outside the worktree (`python3 -c "print(open('/etc/hostname').read())"`) is refused too, by design: the guard does not tell a read from a write inside code. Workaround: write the script into the worktree or the scratch dir and run it as a file (`python3 scripts/read.py`).
- **Git.** `git checkout`, `git restore` and `git reset` pathspecs are judged like write targets (a word git resolves as a commit is not a path). A worker may not set, with `git config` at any scope or `git -c`, a key that makes git run a program: `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.editor`, `core.pager`, `alias.*`, `filter.*`, `diff.*.textconv`, `credential.*`, `include.*`, `includeIf.*`.
- **No worktree.** A worker whose worktree cannot be found (no bound worktree with an owned list, and a cwd outside every prepared one) writes nothing: every write and every inline script is refused with "no worktree known for this worker; the lead spawns workers into one".
- **Force-push.** Refused as for every agent (§11), unless the worktree's allow file lists one. The lead records a one-off authorisation for a worker's `NEEDS` with `node <hooks>/proteus-worktree.js <wt> --allow force-push`; the file is `<git-common-dir>/proteus/allow/<wt name>-<hash>`, outside every checkout. The first force-push the guard lets through consumes the entry, recorded in `<git-common-dir>/proteus-lead/allow-taken/` by the line and a hash of the lines up to it, while the allow file itself is never written by the guard (one per call; a second force-push in the same call is refused), and a call refused for another reason leaves it. No agent can grant one: an agent's `proteus-worktree.js --allow` is refused, and the file is under `.git/`; `proteus-shell-check.js` fingerprints the dir.
- **Deadline.** Tokenising and scanning inline code get 50 ms per command; past that, or on a tokeniser error, the command is refused with "command too complex to judge; split it", as are shells nested more than three deep. File-system and git lookups are not counted, so a slow disk never refuses a command. A command with no write construct costs no more than a verifier's (`tests/workershell.test.js` measures it).

Residuals, for `proteus-shell-check.js` after the call and for the sandbox (#80): what the tokeniser cannot see. Code `eval` or `exec` builds from pieces at runtime, a path assembled from variables or string concatenation in inline code (`'/tm' + 'p'`), a script the worker writes into its owned paths and then runs (`node scripts/x.js`, `make`, an npm script), an interpreter or tool the list does not name (`git` subcommands beyond §11 and the ones above, an archiver other than `tar`/`unzip`), a link that already exists in the worktree (only links the command makes are judged), a path that is outside the worktree only through a link made after the guard ran, and a `>` in `(( ))` whose operand is not a literal path, which dash runs as a subshell redirect. Reads are not limited.

On Claude Code under `install.js --sandbox` (`docs/install.md`, Sandboxed bypass), Bash and its children run in the native sandbox on macOS, Linux and WSL2: writes go only to the repo, its git dir and a private scratch dir, and the network only to GitHub and the registries `## Learned` names. That bounds these residuals for shell commands, not for Read, Edit or Write, or for local MCP servers. Claude Code runs a `statusLine` command outside the sandbox, so `--sandbox` points a Proteus status line whose script sandboxed commands can write at its own copy outside the write set, leaves a foreign one alone with a warning, and warns when the installed plugin itself is inside the write set. That override goes only to `.claude/settings.local.json`, and once a profile exists, `--project`, `--plugin-setup` and `--migrate-here` point a status line they write at the same copy. The profile denies edits to everything under the `.claude/` of the repo root and the guest dir by a rule Linux honours, since a skill's `hooks:` run outside the sandbox and a workflow runs in Claude Code's process. A deeper `.claude/skills/` is denied only by a mid-path rule Linux ignores for shell commands. So the profile is extra protection that blocks many attacks, not a boundary against a determined agent: Claude Code loads and runs project files, such as a nested skill's `hooks:`, from folders the sandbox lets agents write. Known gaps (`docs/install.md`): nested skills, a planted skill the human types, `.claude/agent-memory-local/` read-only for `memory: local` agents, and profiles read only from the current config dir. The container runner (`proteus-container.js`, `docs/container.md`, #80) is the isolation layer for workers. That session runs with `bypassPermissions`, so the review session, where `proteus-verdict.js --post` needs its dialog, runs without it.
