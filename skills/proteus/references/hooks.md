# Hooks

Read when a hook refuses something or you need to know what one checks. The rules they hold are in `enforcement.md`; this is what each hook does and how hooks stay safe themselves.

`install.js --project` runs `install-lead-hooks.js`, which copies every hook to the project's hooks dir and registers the lead's set in `.claude/settings.local.json` (untracked, so a worker's worktree never inherits it); with `--harness codex`, `.codex/hooks/`, `.codex/hooks.json` and `.codex/rules/proteus.rules` (`harnesses.md`). The autostart re-syncs changed hooks from the Proteus checkout at every session start, so a fix reaches every project without reinstalling. All hooks fail open: an internal error never blocks the session.

## Lead hooks (main checkout)

- `proteus-autostart.js` (`SessionStart`): prints the skill body and a `proteus-state` line from local files, so every session opens as the lead at "Session start". The state line also carries `doc-bloat`, `lessons`, `proteus-src`, `proteus-update`, `scratch` (over 1 GB) and `context-mode=missing`; it prints the run-log tail at startup with an open run and after a compaction, and after a compaction the last ten human messages verbatim. Once a day it checks for a newer release, `proteus-update=<tag>`, and with `autoUpdate` on fast-forwards a clean checkout to it once `git verify-tag` accepts it, noting the `CHANGELOG.md` sections in between, or notes why not (`docs/updating.md`). A checkout agents can write (a 1.x home inside a sandboxed repo) is never fetched, updated, moved, copied from or loaded; one line says so (`docs/install.md`, Sandboxed bypass). While the tour is pending it adds one offer line at up to three session starts. It prints the stale-scratch line (`operations.md`) and never sweeps itself (#237).
- `proteus-lead-guard.js` (`PreToolUse`). On the main thread it refuses:
  - edits (`Edit`/`Write`, Codex `apply_patch`) inside the repo except `CONTEXT.md`, `CONVENTIONS.md`, `AGENTS.md`, `docs/adr/*.md`, `docs/lessons/*.md`, the records `.proteus/owned/<id>`, its scratch `<git-common-dir>/proteus/scratch/<key>/` (real path, so no link out, and nothing else under `.git`) and files matching the human's `lead-edits:` globs in `AGENTS.md`, which never cover the guarded paths (`enforcement.md` §11), `teams/`, a link, or a path whose real location is outside the repo (`lib.leadEditDenial`);
  - a spawn (`Agent`, Codex `spawn_agent`) with no model, a model above the lead's, a once-per-project model, or one under the floor, per the ladder (`harnesses.md`, Model ladder); new spawns at `PROTEUS_HANDOFF_HARD` context; worker and verifier spawns while a team skill has drifted (`enforcement.md` §6);
  - `proteus-signoff.js` (`enforcement.md` §1);
  - reading an image (`Read`, Codex `view_image`) unless the human's latest message names the file: each costs ~1.5k tokens, and judging renders is the verifier's or the human's job.
  - In guest mode (`bootstrap.md`) those docs are allowed only in the guest dir, and a subagent edit there during a run is refused like one in the main checkout (except the scout's `teams/*/skills.txt`).
- For the lead and every subagent it refuses a hand-posted commit status or check run (`enforcement.md` §1); reading, editing or naming in a shell the verifier App's key, and a shell that sets `GH_TOKEN` or `GITHUB_TOKEN`; `gh … --edit-last` (one account posts for every agent, so an edit can overwrite a ruling) and an agent's comment the verdict script would count, its first line opening with the word `ACCEPT`, `CHANGES` or `ANSWER`, the human's words (`tracker.md`; one definition, `lib.isVerdict`, for both); a post it cannot read (`gh` through a `$VAR`, `$( )`, `eval` or `xargs`) is refused for that reason, never as a verdict. It asks the human before their verdict post (below).
- Inside subagents it stamps a worker's or verifier's beat for the watchdog on every call, and refuses `run_in_background` Bash, `Monitor`, edits outside the owned paths (`enforcement.md` §2), and in the shell (`lib.agentShellDenial`):
  - a force-push to any branch, its own included, however it is spelled or set up (`--force`, `--force-with-lease`, a `+refspec`, `git config` or `-c` setting `remote.<r>.push`, `remote.<r>.mirror`, a loose `push.default` or a pushing alias); a worker's one the lead allowed passes (`enforcement.md` §13);
  - `git -C`, `--git-dir`, `--work-tree` or `GIT_DIR` aimed anywhere but the agent's own worktree, and a push to `proteus-work/<run>/lead-docs`;
  - `proteus-signoff.js` from a named agent that is not a verifier, or an unnamed one whose brief names a worktree, and `--security` from any but the security verifier;
  - a write to a guarded path by an in-place editor, a redirect, `tee`, `cp`, `mv`, `ln`, `install`, `dd of=`, `truncate`, `touch` or `rm`, after a leading `cd` chain and through `sh -c`, `eval`, `xargs` and `find -exec`/`-execdir`/`-ok`; `find -delete` or an `-exec` writing `{}` under a start point holding one; `rm -r`, `mv`, `cp -r` and `rsync` whose target holds one;
  - `git checkout`/`git restore` of a guarded path from any commit but `HEAD`; `git apply`, `git am` and `patch` whose patch names one or comes from stdin or a file the same line writes; `git stash pop`/`apply` of a stash holding one;
  - a branch moved through the API (`gh api` with a method other than GET on `.../git/refs...`, a graphql `updateRef`/`updateRefs`/`deleteRef`, `gh repo sync --force`).
  - Git Bash and Cygwin drive paths are read as drive paths on Windows, and Codex's shell `workdir` is the cwd the command is judged from. A worker's shell is also confined to its owned paths (`enforcement.md` §13). `$VAR`, `$(...)` and globs are not expanded: `proteus-shell-check.js` catches what got through.
- `proteus-journal.js` (`UserPromptSubmit`): appends every human message to the journal (last 500) with common secrets replaced by `[redacted]` (`proteus-lib.js` `redact`), redacting again when the autostart re-injects them; reminds the lead to log decisions, names open question issues at most every ten minutes, and meters context (`stack.md`).
- `proteus-lessons.js` (`UserPromptSubmit`, `PreToolUse`, `PostToolUse`): trigger-based lesson recall (`lessons.md`).
- `proteus-scratch.js` (`PreToolUse`, `PostToolUse`, `PostToolUseFailure` on `Bash`, subagents included): ledgers each new entry directly in the user's temp dir that the command or its output names; `--path`, `--sweep` and `--size` from the command line (`operations.md`). Only a sweep deletes, and only what the ledger or the scratch dir holds.
- `proteus-shell-check.js` (`PostToolUse` and `PostToolUseFailure` on `Bash`, subagents and worker sessions): see below.
- `proteus-stall.js` (`SubagentStop`, `TeammateIdle`; Codex `SubagentStop` only): refuses a stop that ends waiting on a background job instead of reporting (`operations.md`). A report removes the agent's beat; a stop that passes without one marks it ended, and ends the agent's shell calls for `proteus-shell-check.js`.
- `proteus-statusline.js` (status line): appends `proteus: N questions · M reviews` while any are open, from a cache refreshed in the background at most once a minute. Registered only when the project has no `statusLine` of its own. Codex has none; `inbox=` in `proteus-state` carries the count.

Worker worktree (written by `proteus-worktree.js`, a backup for sessions opened inside a worktree): `proteus-owned-paths.js`, `proteus-owned-check.js` and `proteus-tier.js` (`enforcement.md` §2), `proteus-worker-guard.js` (the subagent rules above, plus no `proteus-verdict.js --post` and no reach for the human's gh login), `proteus-lessons.js`, `proteus-scratch.js`, `proteus-shell-check.js`, `proteus-gates-cache.js`, `proteus-stall.js` on `Stop`.

Not hooks: `proteus-signoff.js` (`enforcement.md` §1; it refuses MERGE while the PR's head branch has an open tamper record), `proteus-security.js` (§1), `proteus-gates-cache.js` (runs a gate unless the same command already passed on the same clean tree, keyed on `HEAD^{tree}`, the dir and the command, passes only, in `<git-common-dir>/proteus/gates/`; refuses below a checkout's top; `roles.md`, `flow.md` step 7), `proteus-watchdog.js` (`operations.md`), `proteus-status.js`, `proteus-ready.js` (`flow.md` step 4), `proteus-merge.js` (`flow.md` step 7), `proteus-cli.js next` (the lead's due actions, one line each: `ASK`, `STOP`, `NUDGE`, `MERGE`, `DECIDE`, `SPAWN verifier`, `SPAWN worker`, `BLOCKED`, then `WAIT` when nothing but `BLOCKED` is due; the mechanical steps it does itself: `SKILL.md`, `flow.md`, `stack.md`. What runs outside the sandbox it runs, as `proteus-merge.js` does, and prints the rest as a `RUN` line, the worktree prep too under `install.js --sandbox`. The prep passes `proteus-worktree.js` the ticket's owned list and `Tier:` (default standard), and `SPAWN worker` names it as `worktree=<path>`; a failed prep is `BLOCKED #<n> prep: <reason>`. The merge batch prints `MERGED PR#<n> <sha12> verdict=<state> by=<login>` per PR, and its suite's `RUN` line again on every call until the result is in; the record PR's verifier checks only that each added file matches its ticket's `Owned:` line and no existing record changed; a verifier spawn's prompt carries its `SPAWN verifier` line's `PR#<n>` and `head=<sha12>`, which the lead guard records so `next` does not list that head again. `proteus-cli.js result` reports the suite to `proteus-merge.js --result` (`flow.md` step 7); its `STOP` lines come from the spawn records, checked against gh), `proteus-intake.js` and `proteus-intake-coverage.js` (`operations.md`), `proteus-goal.js` (one goal-loop round, `operations.md`; refuses unless the sandbox is on), `proteus-pentest.js` (§10c), `proteus-close-report.js` (§5), `proteus-retro.js` (`lessons.md`), `proteus-inbox.js`, `proteus-verdict.js` (`tracker.md`), `proteus-worktree.js` (§2), `proteus-baseline.js` (§12). Each explains its flags with `--help`.

## Tamper check

`proteus-shell-check.js` catches the shell writes `lib.agentShellDenial` cannot read (an interpreter, a variable, a glob, a script file), after the call. Before each subagent shell call the guard fingerprints the guarded paths in every checkout of the repo, a linked worktree's `.git` file, the shared `.git/hooks`, `.git/info`, the git config files and the guard's own records; the user's `~/.claude/settings.json`, `~/.claude/{hooks,agents,skills}`, `~/.agents` and `$CODEX_HOME`'s config, hooks, agents and rules; and the verifier App's key. Each file is its mode and SHA-1, cached by size, mtime and inode (at most 8000 paths); a settings file is hashed without `permissions`. A git config file is compared by key: an agent may set `user.*`, `color.*`, `core.autocrlf`, `core.filemode` and `extensions.worktreeConfig`, and its own branch's `branch.<b>.remote`, `merge`, `description` and `pushRemote` (equal to that remote); any other key changed is named (`git config --unset <key>` puts one back). Its own branch is the one checked out in its own worktree. It also records `git status --porcelain` of each prepared sibling worktree no agent is working in.

After the call it compares. A change git explains passes: a file clean in the checkout's status that came in through commits on `main`, `proteus/*` or their remote copies; a change in a checkout the lead added or removed meanwhile, or in a sibling whose own agent is active, is left alone. Anything else, and any new line in an idle sibling's status, blocks the call naming the paths and opens a tamper record for the agent's branch. Each later call blocks again until every path matches its state before; then the record closes. A deleted record stays open until the lead clears it.

The lead's own shell calls, and the session-start sync, are windows: what changed while one overlapped an agent's call cannot be pinned on either, so it goes to a notice the lead is shown after its call, each path once with the agents whose calls overlapped, cut at about 4 KB; it names `install.js` or `proteus-shell-check.js` when the lead's command ran one. The lead checks each path, has the agent put back what its call did not write, and clears the notice with `node <hooks>/proteus-shell-check.js --clear <n>` (`--clear all`; `--list` prints them). Signoff does not refuse on a notice. A lead call re-baselines: agent calls in flight compare against the state after it, and an open record's path it rewrote takes that state as its state before. An agent's calls end with it: a stop `proteus-stall.js` lets through, or a call older than 40 minutes, no longer counts as in flight.

Residuals: an agent can time a write to overlap a lead call and get a notice rather than a block; an agent call running past 40 minutes is not re-baselined; a lead call whose `PostToolUse` never fires counts as running for up to 15 minutes, and a lead command left in the background is not a window; a write into a sibling whose agent is active is that agent's to notice; a nested checkout inside a guarded dir is not walked; past 8000 entries the fingerprint is cut; a file over 4 MB is compared by size and mtime; an agent can edit a record's items with an interpreter.

## Hook git (#215)

Hooks never let git read a config an agent can write. They run outside the sandbox, and a sandboxed command can rewrite `<common>/commondir`, a worktree's `.git` file, its gitdir's `commondir` or `config.worktree`, or rename that gitdir, any of which hands git a `core.fsmonitor` or a clean filter that runs with the human's rights. So every hook git call goes through one wrapper in `proteus-lib.js`:

- It pins `GIT_DIR` and `GIT_COMMON_DIR` to the repo's common dir, turns off the system and global config, `core.fsmonitor`, `core.hooksPath`, `core.untrackedCache` and submodule recursion, and runs with `-c maintenance.auto=false -c gc.auto=0 -c gc.worktreePruneExpire=never`, so no hook starts the gc whose worktree prune deletes through a planted link (#235).
- It refuses a common dir holding a `commondir` file (an lstat before git starts; a racer between the check and git's read gets past it).
- It reads a worktree's HEAD as a file under `<common>/worktrees/<id>/` and its changes with `git diff` against that HEAD and `git ls-files -o`, never `git status`, on a private copy of its index (a regular file of at most 64 MB, opened without following a link) in a fresh dir under `<git-common-dir>/proteus-lead/`, deleted afterwards.
- Three calls keep the human's config, for their trust and credentials: `verify-tag` and `fetch` on the plugin home or its release clone, and `proteus-merge.js`'s `fetch` of the run branch.

The common dir comes from `CLAUDE_PROJECT_DIR`, not the shell's cwd. It must be a real `.git` dir above `<main>/.worktrees/<id>`, `<main>-proteus/<id>` or `<main>/.claude/worktrees/<n>`, or at the project dir. A dir in none of its checkouts gets no git at all: there the hooks act as outside git. `install.js --project <dir>`, which the human runs, takes that dir's repo. A known gap (#231): outside the pinned copy below, a layout none of these match falls back to following `.git` files and `commondir`.

`proteus-worktree.js` runs outside the sandbox, so it prepares only a worktree the common dir registers. Under `install.js --sandbox` its excluded copy takes the main root and state dir from `sandbox-root.json` beside it (`lib.pinProject`) and writes nothing in a dir sandboxed commands can write (`docs/install.md`, Sandboxed bypass); everything else in preparing a worktree is written by the in-repo script inside the sandbox. The worker's own hooks and config are not a boundary; CI's check against `.proteus/owned/<id>` is.

`proteus-merge.js` runs outside the sandbox too, so it does only `gh` merges (without `--delete-branch`), the fetch (`--no-recurse-submodules`, `core.alternateRefsCommand=true`, origin's URL from `<common>/config` alone), ref reads and its own state file: no git with a working tree or an index, nothing under `<common>/worktrees`, nothing from `.worktrees/_run` or a PR. The suite loop is `flow.md` step 7. `proteus-run-tree.js` has no sandbox exclusion (a test holds this); it remakes `<main>/.worktrees/_run` per commit as a plain `git init` with the project's objects through alternates, checks its tree against the commit's, and refuses a `.worktrees` or `_run` that is a link. The merge state `<common>/proteus/merge/<run>.json` is written only as a new file and read only as a regular file (#226), and every read is validated (positive PR and ticket numbers, full commit ids, bisect bounds in range, worker branches). On pass it prints origin's tip only when it equals the state's commit, and names the merged branches re-read from `gh pr view`, never from the state; control characters are stripped from all it prints.

## Lead state (#236)

Agents can write `<git-common-dir>/proteus/`, so every file a hook (or an unsandboxed lead script) creates, rewrites, appends, renames or deletes lives in `<git-common-dir>/proteus-lead/`: the journal, bindings, spawn records, beats, tamper records, lead windows and notices, the guard's hash cache, the inbox and drift caches, lesson hits, the scratch ledger and the `--allow` entries already used. `lib.leadDir` refuses, writing nothing, when that dir or one under it is a link or not the user's. A rewrite is a temp file created with `wx` and renamed, an append opens with `O_NOFOLLOW`, a removal unlinks the link, never its target; `leadCreate` lstats first, as Windows' `wx` creates through a dangling link. On first use the lead's files are copied over from `<git-common-dir>/proteus/` (regular files only). What agents and lead scripts write there (the scratch dirs, `allow/`, `guest.json`, `gates/`, `forgotten.json`, `profile.json`) is read as untrusted (a regular file, not followed, size-capped) and never written back. Every notice is checked when shown (a positive integer `seq`, numeric times, printable strings of at most 512 characters); one that fails is dropped and named on stderr. No hook deletes under the scratch dir or runs `git worktree remove` or `prune`; the sweep runs `git worktree prune` only when every entry of `<git-common-dir>/worktrees/` is a real dir holding a regular `gitdir` file. `install.js --project` writes the `.git/info/exclude` lines; `install.js --sandbox` makes `proteus-lead` (mode 0700) before writing the profile, which denies writes to it. Without the profile, an agent with unsandboxed shell access can still edit the lead's state.

## The human's verdict

An `ACCEPT`, `CHANGES` or `ANSWER` counts only from the human's login (`proteus-verdict.js`). With a login of their own for the agents (`identity=separate`), the review session posts it under the human's through one command: `node <hooks>/proteus-verdict.js <issue> --post --body-file <file> --sha <sha256>`. It posts the file's bytes when their sha256 is still `<sha256>`, the first line opens with a verdict word, the issue is labelled `proteus-review` or `proteus-question`, and the human's gh login (`GH_CONFIG_DIR` dropped, so gh's own default, or `humanGh` in `~/.claude/proteus.json`) is `human`.

The lead guard runs on that command in every session, `PROTEUS=0` included (`lib.humanPost`). On the main thread it reads and hashes the body file and answers `permissionDecision: "ask"`: the human sees the issue, its title, the login and the body's first lines and approves or declines. A missing or stale `--sha`, a body with no verdict word, the human's gh logged in as someone else, or the command in any other form are denied first; subagents, teammates and worker worktrees outright. Where the dialog cannot reach the human the guard denies and prints the command for the human's own terminal:

| Session | Hook `ask` | Proteus |
|---|---|---|
| `default`, `acceptEdits` | the permission dialog | ask |
| `auto` | a dialog from Claude Code 2.1.211; before, the classifier could approve it unseen | ask from 2.1.211, deny when older or unknown |
| `plan`, `dontAsk`, `bypassPermissions` | no command runs, the prompt is denied, or prompts are off | deny, print the command |
| `-p` and the Agent SDK (`CLAUDE_CODE_ENTRYPOINT=sdk-*`) | answered by the program, not the human | deny, print the command |
| no or unknown `permission_mode` | unknown | deny, print the command |
| Codex | no ask: its `PreToolUse` hooks allow or deny | deny, print the command |

Sources: https://code.claude.com/docs/en/hooks (PreToolUse decision control, `permission_mode`), https://code.claude.com/docs/en/permission-modes, https://code.claude.com/docs/en/headless; checked against Claude Code 2.1.302.

While `agentGh` is set, the guards keep every agent, the lead and the review session included, off the human's login (`lib.humanGhDenial`): Read, Edit and any shell word naming a path in the human's gh config dir (also a guarded path for shell writes), a shell that sets or unsets `GH_CONFIG_DIR` or `GH_HOST` or runs `env -i`, `gh --hostname`, and `gh auth login`, `logout`, `switch`, `token` and `refresh`. As with the App's key, a script, an interpreter or the OS keyring still reaches the login; the boundary is the human's click and the verdict script's author check.

## Harnesses and agent names

No hook reads Claude Code's hook JSON itself. `proteus-harness.js` loads the adapter named by `PROTEUS_HARNESS` (`proteus-harness-<name>.js`, default and fallback `claude`), which turns the CLI's input into one Proteus event, answers for the hook, reads the transcript, and knows where the CLI keeps settings, agents and worker hooks; the contract is at the top of `proteus-harness.js`. Hooks under `.codex/hooks` use the Codex adapter. The default model ladder belongs to the adapter; a CLI without one runs every spawn on the lead's model until `models.ladder` is set.

Every guard decision that turns on an agent's name reads it through `lib.agentName`, which strips a leading `proteus:`, the namespace a Claude Code plugin gives its agents (#136). Only that one: `evil:proteus-verifier` counts as a named agent that is no verifier, worker or scout, since any plugin can ship an agent under a Proteus name.

`PROTEUS=0 claude` (`PROTEUS=0 codex`) opens a plain session with none of the lead's hooks but the verdict checks: the review session, or the human working by hand. `node <Proteus checkout>/install.js --doctor` checks the whole install, `--doctor --fix` repairs what it safely can.

## Policy (#307)

- `proteus-policy.js` is the policy engine; no guard calls it yet. `show [--json]` prints the effective policy and where each value came from, `check '<json event>'` the effect for `{ "tool": "shell"|"edit", "command", "path" }`, `render` the project's `POLICY.md`, and `write <draft.json> [--user]` writes a draft only when it validates (exit 2 and nothing written otherwise).
- Layers, each overriding the last: the preset (`templates/policy/presets.json`: `hands-off`, `balanced` by default, `careful`), the user file `proteus-policy.json` beside `proteus.json`, and the project's `teams/policy.json`. Rules merge by `id`; when several match, block beats ask beats allow.
- An invalid file counts as absent and its errors are reported. `teams/POLICY.md` is rendered from `teams/policy.json` on every write; nobody edits it by hand.
- The policy guards against mistakes, not an adversary: a pattern can be worked around. The fixed core in `enforcement.md` stays the hard boundary.
