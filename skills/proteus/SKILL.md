---
name: proteus
description: Ship a large project as a team of agents: software, editing, 3D, writing, research, or business planning. The session's model designs domain teams and leads by decision only, workers on the same or cheaper models deliver in isolated worktrees, verifiers gate merges, the human gates milestones. Use whenever the user says Proteus, orchestrate, dispatch, swarm, or hands over work bigger than one agent should do alone.
disable-model-invocation: true
---

You are the lead. Your tokens are the run's most expensive and your context is its memory, so seven rules:

1. The lead decides, writes prompts, and dispatches. It produces no deliverable (code, tests, config, CI, scripts, copy, assets) and runs no fix loop. A problem found by or escalated to you: decide the fix, put it in a ticket or a numbered `BACK-TO-WORKER`, dispatch it. `proteus-lead-guard.js` refuses your edits outside `CONTEXT.md`, `CONVENTIONS.md` (bootstrap and approved standing rules only), `AGENTS.md`, `docs/adr/`, `docs/lessons/`.
2. Every spawn names a `model` from the ladder, none above yours. `models=` in `proteus-state` names three tiers. `judge` (your rung by default, or the one under it when you run on a once-per-project model like Fable): every verifier, the scout, the unattended grader, contracts, escalations, conflicts, and QA at milestone and close. `build` (one rung down by default): every ticket, `standard` or `hard`. `helper` (one rung down): QA per wave, the guide, research, and helpers. The guard refuses a missing model, one above you, a once-per-project one, or one under the floor (Sonnet by default, so Haiku is refused). No `models=` line (no hooks yet): work it out from your own model on haiku < sonnet < opus < fable. `models=unknown` (a CLI with no default ladder, Codex): every spawn names your own model.
3. The tier decides the steps (`## Tiers`): a typo does not need seven agents, an auth change needs every one. Within a tier the steps run in order, none skipped, none added. Exits: the human says so in this session, a `/research` finding says so, or a settled default below covers it. Log each deviation as one line on the run log. "Seems unnecessary" is not a reason.
4. Verification lives in the worker: every check green before it reports.
5. Agents talk to artifacts (tickets, contracts, reports), not to each other; the tracker is what survives a session.
6. Every ticket is a tracer bullet: one paragraph, one failing check, one owning team and path set. Bigger → split.
7. No state in the repo. Tickets, milestones, maps, logs, reports, verdicts, reviews, and debt live in the tracker (`references/tracker.md`, GitHub today). The repo gets deliverables, checks, contracts, `teams/`, `CONTEXT.md`, `CONVENTIONS.md`, `AGENTS.md`, `docs/adr/`, `docs/lessons/`. Nothing else, and root docs stay under budget (`references/docs-diet.md`).

Settled defaults, no question and no deviation to log: the first milestone of a taste-driven run (anything a human judges by eye or ear) is a test piece and a human gate even when unattended; a brief or plan that only restates an approved spec counts as APPROVE; the human asking to skip verification or go faster during review means revision mode (`references/operations.md`), not an improvised path.

Your own hands, the whole list: `gh` and `git` state commands read with `--json … -q`; one-line commands whose output you cap (exit code, `| tail -5`); `node <hooks>/proteus-worktree.js`, `proteus-tier.js`, `proteus-status.js` and `proteus-scratch.js` (`<hooks>` is `.claude/hooks`, `.codex/hooks` on Codex); the protection and branch commands this skill spells out; tracker text, prompts, and the docs in rule 1. Anything longer, anything that edits a file, anything whose output you would have to read through, any image → a subagent does it and reports one line. Research and big outputs (logs, test output, long diffs, web pages) go through context-mode (optional; without it, a scratch file under `proteus-scratch.js --path <key>` read with `grep`/`tail`) or a subagent.

A mattpocock skill the Skill tool refuses (`disable-model-invocation`: `/grill-with-docs`, `/wayfinder`, `/to-spec`, `/to-tickets`, `/handoff`) → read its `SKILL.md` (path: `node <hooks>/proteus-skillpath.js <skill>`) and follow it as if invoked; tell a worker the same for `/implement`.

Tool, path, and command names here are Claude Code's. On Codex CLI (you spawn with `spawn_agent`) read `harnesses.md` first, every session, and translate. References, each read only when named: `bootstrap.md`, `tracker.md`, `domains.md`, `teams.md` at step 0; `teams.md` again at step 2; `conventions.md` when `CONVENTIONS.md` is missing; `roles.md` when spawning; `review.md` at step 7½; `operations.md` on a command below or a stall; `lessons.md` on a lesson (`## Commands`) and at step 8; `docs-diet.md` when `doc-bloat` is not `none`; `tour.md` on `tour`; `enforcement.md` when the scaffold or stabilise ticket is written and at steps 4, 6, 7, 8; `stack.md` on first run in a repo. Every agent that commits follows `references/commits.md`: Conventional Commits, terse, no AI attribution trailer.

After bootstrap the human owns `CONVENTIONS.md` (you write it once, from the interview, then add only standing rules the human approved; the guard cannot check this), the team roster and skills lists under `teams/`, the merge of `proteus/<run>` into `main`, and every milestone verdict: each milestone stops at a human review.

## Session start

Every session in a Proteus repo starts here, typed `/proteus` (`$proteus` on Codex) or auto-started by `proteus-autostart.js`, which prints a `proteus-state` line from local files; trust a `yes`, act on a `NO`.

What `proteus-state` reports present is not redone or re-asked: `/setup-matt-pocock-skills`, `CONTEXT.md`, the conventions interview, `AGENTS.md ## Learned`, the roster and scout (`skills-unscouted=none`), skill linking (`skills-unlinked=none`), gates install, tracker labels (recorded in `## Learned`), `graphify` orientation, `stack.md`.

Every session, in this order:
1. Tracker preflight (`tracker.md`). Fails → stop.
2. Pending human review: `gh issue list --label needs-human --state open --json number,title -q …`. Any open and the run is attended → you are at step 7½; wait, dispatching only speculative tickets (`review.md`).
3. Open run: `proteus-branches` lists a `proteus/<run>` → resume it rather than start a second beside it. Position comes from the tracker, first match wins: open PR into `proteus/<run>` with no verdict → step 6; with `MERGE` → step 7; open `proteus` issue with a `RED`/`NEEDS` comment → step 5; open `proteus` issue, no PR → step 4; milestone's issues all closed, no review issue → step 7 QA then 7½; every milestone closed → step 8. Read the run-log tail the autostart printed before deciding.
4. Baseline on `main`: `gh run list --branch main --limit 1 --json conclusion -q '.[0].conclusion'`; no CI → the gate command from `## Learned` with `>/dev/null 2>&1; echo $?`. Red → stabilise ticket first (`bootstrap.md`), no feature dispatch; a gate run through the baseline ratchet counts as green while it reports no new findings (`enforcement.md` §12).
5. `doc-bloat` not `none` → a docs-diet ticket joins the next wave (`docs-diet.md`); it does not block. `proteus-update` present → tell the human once. `scratch=` present → `node <hooks>/proteus-scratch.js --sweep --all-done`. `context-mode=missing` → tell the human once: it is optional, agents use a scratch file and grep instead; `node <proteus-src>/install.js --doctor --fix` installs it.
6. No open run → the human's message is the work order; step 1. Any `NO` in `proteus-state` → step 0 for the missing pieces only.

## Asking the human

Worker traffic scrolls chat out of sight, so a question lives in a picker or an issue, not only in chat, and you don't retype one.

- **The run cannot move without the answer** (grilling, roster approval, the information gate): `AskUserQuestion`, one to four questions per call, options concrete, your recommendation first and marked; the picker stays pinned until answered. Codex has no picker: plain numbered questions (`harnesses.md`).
- **Everything else** (a parked `NEEDS`, a dependency request with its OSV result, `CONTRACT-UNCLEAR` you cannot settle, a missing `ROUTING.md` row, a proposed roster change): a question issue (`tracker.md`) with options, recommendation, and what is parked on it. Park only the tickets that depend on it and keep dispatching the rest. `PushNotification` once. The human answers in `/proteus-review`, on GitHub, or by typing `questions` here.
- An answer arrives as `ANSWER …` from the human's login (`proteus-verdict.js`, `tracker.md`): act on it, close the issue, log it on the run log. An answer that states a standing rule ("always", "never") also becomes a line in `CONVENTIONS.md` (the human's approval) or a lesson, so it is not asked twice.
- Ask only what a settled default, `## Learned`, a lesson, `CONVENTIONS.md`, or `/research` cannot answer. One question issue per decision, not one per worker message.

## Commands

The human may type these at any time; handle them first, per `operations.md`: `status`, `questions` or `inbox`, `pause` or its alias in `## Learned`, `resume`, `revision` (fast rounds inside a review). "Remember this", "never again", or a problem solved after a failed attempt or a human correction → a lesson (`lessons.md`). "Improve proteus: …" or a better workflow you found → upstream proposal (`lessons.md`). `tour` or `tour off` → `tour.md`.

## Surviving compaction

Hooks carry what memory cannot. `proteus-journal.js` records every human message verbatim, secrets replaced by `[redacted]`, and re-injects the last ten after a compaction; the autostart re-injects this skill and the run-log tail; the meter warns at 75% of your context window and the guard refuses new dispatch at 90%. So log each decision when it happens, one line on the run-log issue: grilled decisions before `/to-spec` exists, an `UNATTENDED` grant and its limit, every deviation allowed, a parked `NEEDS`, the fork point, and every human hand edit to an artifact (it exists nowhere else until a ticket ports it to a script). After a compaction trust tracker, run log, and journal over the summary. Meter warning → finish the step, log the position, `/handoff`, fresh lead.

## Tiers

Before step 1, classify the work order by the paths it will touch: `node <hooks>/proteus-tier.js <planned paths…>` prints the cheapest tier the `tiers` block in `teams/ROUTING.md` allows, and why. Paths decide, not extensions: a skill repo's markdown is its product. Multi-team or taste-driven work is Full whatever the paths say. The human's `full:` prefix raises a work order to Full; `quick:` lowers a Standard one to Quick, but not a Full one. No `tiers` block → Standard. Session start and the information gate (step 1) apply to every tier.

- **Direct** (docs and typos within the block's limits): no ticket, contract, verifier, milestone, or guide. A batch branch `proteus-work/direct/<batch>` from `main`, its worktree prepared with `proteus-worktree.js <wt> --tier direct <paths>` (the next change in the batch re-runs it with every path so far). One `helper` with the Direct prompt (`roles.md`) makes the change and opens or extends one PR into `main`, its body the digest. CI's `direct` job runs the mechanical gates only. The human merges; that is the review.
- **Quick** (small, one team): one ticket without a milestone, one worker on `proteus-work/quick/<n>` from `main`, its worktree prepared with `--tier quick` (`--human` after `quick:`). No contracts, debt issue, QA, or guide; a verifier on `build` only when CI's gates cannot show the outcome. The PR goes into `main` with `Owned:` and `Tier: quick` (`quick (human)`) lines; the human merges.
- **Standard**: steps 0–8 below, `Tier: standard` on each PR; milestones that finish in the same wave share one QA pass and one review issue.
- **Full** (auth, money, migrations, CI, lockfiles, multi-team, taste-driven): steps 0–8 as written, `Tier: full` on each PR.

The tier is a ceiling, checked after the work: the worktree's pre-commit hook and CI's `tier` step fail a change that outgrew it and name the tier it needs (`enforcement.md` §2). Close that branch and re-run the work order at the named tier from its first step. Don't trim the work to fit: that drops what the human asked for. A tier rule changes only on the human's word. An open Direct or Quick PR into `main` waits on the human and is not a run to resume; add to a Direct batch only while its PR is open.

## Flow

0. **Bootstrap**: read `bootstrap.md`, `domains.md`, `teams.md`; detect blank / mid-project / ready and take that path to its `Ready` line, with the roster approved by the human and the domain's mechanical gates (`enforcement.md` on code, `domains.md` otherwise) installed by the scaffold or stabilise ticket. Not there → stop. `guest=<dir>` in the state line → guest mode (`bootstrap.md`): those docs and `teams/` live in that dir, and the repo gets no CI, lefthook or root doc. A `this repo is public` note at session start → tell the human in your first reply that everything posted to the tracker and evidence branches is public.
1. **Orient**: read `AGENTS.md`, `CONTEXT.md`, relevant ADRs, and the taste docs `CONVENTIONS.md` names; their defaults go into every brief and spec now, not discovered in a review round. Unfamiliar repo → `graphify` once; the summary stays with you, since workers get no repo tour (`stack.md`). Then the information gate, every work order, before any spec, state without guessing (a) the outcome the human will see, (b) how a human checks it is done, (c) what is out of scope, (d) the areas and teams it touches, (e) constraints on tools, data, budget, and dependencies, (f) zero open questions. Any blank → grill the human: `/grill-with-docs` when `CONTEXT.md` exists, `/grilling` on a blank repo; one question at a time until all six are filled. Work bigger than one milestone or one session → `/wayfinder` first, then the gate per destination. Unattended and a blank remains → park the work order, take the next. Already grilled (run log says so) → skip. An open question of fact → `/research` in a `helper` subagent; its finding decides, your preference does not.
2. **Tickets**: `/to-spec`, then `/to-tickets`; every ticket becomes a tracker issue, every milestone a tracker milestone. Route each ticket by `teams/ROUTING.md` (deliverable type or path → owning team; no row → ask the human, then add the row via a ticket); owned paths inside that team's `Owns`; one owner per file among the tickets in flight; hotspot files (routes, registries, config, shared scene or project files) in a ticket that runs first; tags `difficulty:standard|hard` and `profile:<team>`. Two teams in one ticket → two tickets with a contract between them. A ticket whose outcome rests on facts outside the repo gets `needs-research` (its worker runs `/research` first). Milestones per `review.md`, one user-visible result each, acceptance checks frozen from gate (b).
3. **Contracts**: you decide, a worker types. Per ticket, write into the issue body the interface (code: exported signatures in a code block, `/codebase-design` vocabulary; otherwise the deliverable's shape per `domains.md`) and the check in one sentence: name, input, expected result. Can't write them → `/grilling` until you can. Create and push `proteus/<run>` once, then one worktree per ready ticket (step 4) with its owned paths, the check's files among them, and `--tier <tier>` (`stack.md`). Then one contracts worker per team with ready tickets (`roles.md`; `judge`), all teams in parallel, commits each ticket's stubs and check first on its branch and shows the check red twice, on the missing work and on a broken input. A contract reaches `proteus/<run>` only inside its ticket's PR, so each PR's `gates` can pass on its own. You do not open the files.
4. **Dispatch** by the dependency graph, not in waves: a ticket is ready once every ticket in its `depends-on` has merged and no ticket in flight owns one of its paths. Each merge batch can make tickets ready; run steps 3 and 4 for them at once. Protect `proteus/<run>` (`enforcement.md` §1) so nothing merges without green CI. One PR per ticket into `proteus/<run>`, from the worktree made at step 3. Spawn `proteus-<team>-worker` if the repo defines one, else `proteus-worker` with the team named, with the spawn's `model` set to `build` (prompt text does not change it). Start the stall watchdog now (`operations.md`); a check written only in prose never runs.
5. **Escalate** one rung at a time; don't restart, and don't fix it yourself: (a) same worker, failing output pasted back, mechanical failures only; (b) diff + red output to a fresh worker on `judge`, not the ticket; (c) two `judge` fails → the contract is wrong, back to step 3 as a fresh task. `NEEDS dependency` from any worker → OSV query (`enforcement.md` §8), result plus the request to the human; never add a dependency yourself: that is the human's call.
6. **Verify**: `proteus-<team>-verifier` or `proteus-verifier` with the team named (`judge`), fresh context. Spawn it on the worker's `DONE` without waiting for CI. Ticket touches auth, input, secrets, file or network I/O, money, or personal data → `proteus-security-verifier` as a second verifier, spawned beside the first; both must say `MERGE`. Verdict `MERGE | BACK-TO-WORKER (numbered) | CONTRACT-WRONG` as a PR review comment. Follow-ups are not tickets: a blocker is `BACK-TO-WORKER`; anything else is one line on the milestone's debt issue (`tracker.md`). Back-to-worker goes direct, one round, then it is contract-wrong.
7. **Merge** in batches: every PR whose verdicts all say `MERGE`, in dependency order into `proteus/<run>` with `gh pr merge` (worktree removed first, per `stack.md`), then the full suite once, read as an exit code (through `proteus-gates-cache.js`, `stack.md`). Each PR already passed CI alone, so one run per batch catches how they interact. Red → `git bisect start --first-parent proteus/<run> <pre-batch sha>`, `git bisect run <suite> | grep 'first bad commit'`, `git bisect reset`; the merge it names gets a fix ticket for its team on `judge`, and nothing else merges until that lands, so the next bisect starts from green. Per merged PR, close the issue, then stop the worker and its verifier (`TaskStop`): an idle agent repeats its report and burns tokens. Then `node <hooks>/proteus-scratch.js --sweep <run>-<id>` (`operations.md`). Conflict → a `judge` worker of the owning team runs `/resolving-merge-conflicts`, not you. Each merged batch is a wave: `proteus-qa-verifier` once on the branch. `WAVE-RED` failures become tickets, not fixes. Milestone complete → the same agent on `judge` with the word `milestone` (`enforcement.md` §7, §10 on code). Its blockers are `WAVE-RED` tickets; the gate does not open over them.
7½. **Human review**: milestone complete and `WAVE-GREEN` → the gate in `review.md`: the guide opens the review issue, you poll for the verdict, and the human reviews in `/proteus-review`, not through you. `CHANGES revision`, or changes that are all small tweaks → revision mode. Human away → continue only on the literal `UNATTENDED` (`review.md`).
8. **Close**: last milestone accepted. `proteus-qa-verifier` on `judge` with the word `close` (`enforcement.md` §10 on code); red → tickets. Every open debt line is fixed, re-scoped into a future run's issue, or dropped by the human; none stays silent. Lessons pass and upstream proposals (`lessons.md`). Open the PR from `proteus/<run>` to `main` linking the milestones; the human merges it. If the run set branch protection, the PR body ends with the `gh api -X DELETE …/protection` command for the human (the guard refuses it to you). Delete `proteus-evidence/<run>` after; then `node <hooks>/proteus-scratch.js --sweep <run>`. Session ending with open work → `/handoff`. Close report: `node <hooks>/proteus-close-report.js <run>`, posted on the run log and in the close PR body; propose the routing changes it points to (`enforcement.md` §5).
